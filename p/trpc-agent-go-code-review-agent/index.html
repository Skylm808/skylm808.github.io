tRPC-Agent-Go 源码导读：如何构建一个可审计的 Go 自动代码评审 Agent

本文基于 tRPC-Agent-Go 的官方实例文章 《tRPC-Agent-Go：构建智能 AI 应用的 Go 语言 Agent 框架》，分析 examples/code_review_agent 如何把 Skill、Tool、CodeExecutor、PermissionPolicy、Artifact、Event 和 Telemetry 组合成一个 Go 代码评审 Agent。

这不是一篇“如何调用 LLM 评论代码”的文章。我们要回答的问题是：如果评审任务需要读取 diff、运行检查、保留审计记录，并且不能让模型或脚本越权，Agent 应该怎样组织？

一、项目要解决什么问题

一个真实的代码评审通常包含这些步骤：读取 PR 改动、定位新增行、检查安全和生命周期风险、必要时运行测试、给出带证据的建议、通知人工复核，并保留历史记录供回放。如果只把整个 PR 文本发给模型，会遇到三个问题：

  1. 模型不一定能稳定对应到文件和行号。
  2. 模型不应该直接决定执行哪些 shell 命令。
  3. 评审失败、权限拦截和低置信结论不能只留在终端日志里。

这个示例的输入可以来自统一 diff 文件、PR patch、文件列表、Git 工作区或测试 fixture。它先用确定性 Skill 规则处理高置信问题，再在权限允许时执行容器检查，最后生成 JSON/Markdown 报告并写入 SQLite。

二、先看框架组件，再看 CR 业务代码

官方实例把 tRPC-Agent-Go 定位为构建生产级 Agent 系统的 Go 框架。CR Agent 实际使用的是下面几类组件：

框架组件 解决什么问题 在这个示例中的落点
Agent / Runner / Event 组织一次 Agent 运行，并把阶段结果以事件流传递 Agent.Run、Runner adapter、输入/沙箱/模型/结束事件
Skill / tool/skill 把可复用工作流封装为 SKILL.md、文档和脚本 skills/code-review/、skill_load、skill_run
Tool 给 Agent 一个受控的外部能力入口 LoadTool、RunTool、codeexec
CodeExecutor 在本地、容器或其他 runtime 执行代码 默认 codeexecutor/container，本地仅 fallback
PermissionPolicy 在 Tool 真正执行前检查命令是否允许 固定放行 scripts/check.sh、go test、go vet
Artifact 描述和保存报告等运行产物 JSON、Markdown、诊断文件的 digest/大小/路径
Telemetry 记录一次运行的耗时、事件和异常 review trace、tool call、severity 和 exception 指标
Model adapter 抽象不同模型 Provider fake、HTTP、OpenAI-compatible 可选接入

SQLite、diff parser、规则库、报告模板和 CR 的编排逻辑是这个 example 自己写的业务层。它们通过接口接入框架，但不是 tRPC-Agent-Go 自动生成的代码评审能力。

官方组件总览和这个示例的初始化位置分别见：官方框架介绍 和 Agent.New。

PR patch 只是 GitHub 将某个 PR 的改动导出的 unified diff 文本。例如：

这里 2240 是 PR 编号，--repo 是仓库，--patch 是让 CLI 以 patch 格式输出，> 才是把终端输出写到本地文件。.patch 是常见文件名后缀，解析器真正关心的是内容格式。GitHub 也提供 /pull/2240.patch 和 /pull/2240.diff 形式的响应。

func Read(cfg Config, req Request) ([]byte, string, error) {
    if req.DiffFile != "" {
        return readFileWithLimit(req.DiffFile, maxBytes, "diff file")
    }
    if req.FileList != "" {
        return diffFromFileList(req.FileList, req.RepoPath, maxBytes)
    }
    if req.Fixture != "" {
        return readFixtureInput(cfg.FixturesRoot, req.Fixture, maxBytes)
    }
    if req.RepoPath != "" {
        return diffFromRepo(req.RepoPath, req.BaseRef, req.HeadRef, maxBytes)
    }
    return nil, "", errors.New("diff file, file list, repo path, or fixture is required")
}

这个函数的价值是让后面的代码不关心输入来自 PR 还是本地工作区。所有输入最后都变成一份 []byte unified diff。

type ParsedDiff struct {

type ParsedFile struct {
    Path, Language string
    PackageName    string
    Hunks          []Hunk

type Hunk struct {
    File               string
    OldStart, OldLines int
    NewStart, NewLines int
    Context            []string
    CandidateLines []int
    Lines          []Line
}

type Line struct {
    OldLine, NewLine int
    Kind, Text       string
}

规则只扫描新增行，但保留 hunk 上下文。例如 context.Background() 是否危险，需要知道函数是否已经接收 ctx；循环中的 defer 是否危险，需要知道前面是否存在循环边界。parser 把这些上下文保留下来，避免规则只能看孤立的一行。

3. PermissionPolicy

internal/approval/gate.go 将可运行命令做成 allowlist：

1
2
3
4

go test ./...                                allow
go vet ./...                                 allow
go test ./... && curl ... | sh                ask
rm -rf /repo                                  ask

在这个项目里，PermissionPolicy 不是“用户确认弹窗”的装饰，而是进入 Tool 执行器前的安全边界。权限请求里包含 Tool、Tool 名称、声明和实际参数，策略可以判断“调用的是哪个能力”和“传入了什么命令”。

for _, file := range diff.Files {
    for _, hunk := range file.Hunks {
        for _, line := range hunk.Lines {
            if line.Kind != "add" {
                continue
            }
            text := strings.TrimSpace(line.Text)
            if shouldReportSecret(text) {
                out.Findings = append(out.Findings, review.Finding{
                    Severity: "critical", Category: "security",
                    File: file.Path, Line: line.NewLine,
                    Title: "Potential secret appears in added code",
                    Evidence: redact(text),
                    Recommendation: "Replace the literal with a secret manager or environment lookup.",
                    Confidence: "high", Source: "rule",
                    RuleID: "secret-leak", Status: "finding",
                })
            }
        }
    }
}

这次输入的真实流转是：

  1. parser 识别 config.go 和新增行号。
  2. 规则只扫描 line.Kind == "add" 的代码。
  3. shouldReportSecret 命中 API Key 形态，生成 critical/security finding。
  4. Evidence 在规则输出前经过 redact，报告能给出证据但不复制 Key 明文。
  5. finding 带 rule_id=secret-leak，后续报告、指标、回归测试可以稳定识别它。

同样的思路用于 context.diff：规则发现已有 context 语义的函数里重新创建 context.Background()，指出取消信号、deadline 和 trace context 可能丢失。相关规则在 rules.go 的 context-background-misuse 分支，fixture 在 testdata/fixtures/context.diff。

当前规则是“新增行 + hunk 上下文”的确定性启发式，不是完整 Go AST/SSA 分析。它的优点是可解释、可快速测试；跨文件授权、业务状态一致性等规则才交给可选模型补充。

2. 容器边界

internal/execution/exec.go 的 container 配置负责：

  • 禁用网络，避免脚本外传源码或临时下载依赖；
  • 只读挂载待审仓库；
  • 限制 CPU、内存和进程能力；
  • 只传递白名单环境变量；
  • 用 timeout 和输出上限记录失败而不是让进程失控。

因此容器中执行 Go 检查有一个明确前置条件：仓库需要准备 vendor/modules.txt。如果依赖未 vendor，程序记录 unsupported 能力审计，不联网下载。staticcheck 当前仅允许 local-fallback，E2B runtime 是预留入口，不能在面试中说成已完成。

九、模型阶段：只做语义增量

模型阶段在 internal/llm/review.go。发送给 Provider 的输入不是原始 diff，而是：

1
2
3
4
5
6
7

input := Input{
    DiffSummary:       review.RedactSecrets(string(diff)),
    InputMetadata:     inputMeta,
    ExistingFindings:  SanitizedFindingSnapshot(result.Findings, result.Warnings),
    SandboxSummary:    result.SandboxSummary,
    GovernanceSummary: result.GovernanceSummary,
}

模型输出会经过 validateProviderFindings，确认 file/line 锚定在当前 diff 的新增行；没有锚点的模型问题被丢弃，同时增加 model-invalid-anchor 人工复核项。MergeFindings 再按 DedupeKey 去重，并按 confidence 决定进入 findings 还是 warnings。

这就是“规则优先、模型可选”的边界：确定性风险不依赖模型，模型只处理跨文件授权、事务语义、业务状态一致性等规则难以直接判断的内容。没有 API Key 时，fake provider 和 dry-run 仍能覆盖主流程。

1. SQLite 是业务层的审计存储

2. 为什么用事务写 SaveReview

SaveReview 先 BeginTx，再写子表，任何步骤失败都会 rollback。否则可能出现 task 已完成但没有 sandbox run、报告生成但 finding 未落库等审计断链。

3. Artifact 与报告

tRPC-Agent-Go 的 artifact 组件提供统一产物服务边界。这个示例将 review_report.json、Markdown、中文报告和 diagnostics 作为 artifact 记录，并在 internal/agent/persist.go 保存 digest、大小、路径和创建时间。这样可以知道报告是否被替换，也能在数据库中回放某次 review 的产物引用。

4. Event 和 Telemetry

Runner adapter 将输入加载、Skill 执行、沙箱运行、模型调用、任务完成或失败包装成官方 event；Agent.Run 消费任务结束事件，读取 StructuredOutput 作为最终 review.Result。同时 runDirect 用 telemetrytrace.Tracer 创建 cr-agent.review span，写入 task ID、模式和阶段耗时。Event 适合实时观察，Telemetry 适合统计和追踪，两者不是一回事。

十二、面试时的几个关键追问

为什么要把 Skill 和 Agent 编排分开？

Skill 是可版本化、可复用的工作流包，包含 SKILL.md、规则说明和脚本；Agent 负责输入、权限、执行、模型、报告和持久化。这样规则可以单测和复用，权限策略也能对稳定脚本入口做最小授权。

为什么 skill_run 也要 PermissionPolicy？

因为脚本本身就是执行能力。即使脚本来自仓库，也可能被更新或组合出额外命令。NewRunTool 的 allowed command 和 PermissionPolicy 是两层边界：第一层限制 Skill 脚本范围，第二层检查实际 Tool 参数。

为什么容器要禁网？

审查输入可能包含源码、密钥或内部路径，禁网可以减少外传风险；同时防止 go 或脚本在评审时下载不受控依赖。代价是必须准备 vendor，程序会把不满足条件记录成 unsupported，而不是静默联网。

沙箱失败会不会让整个 review 失败？

不会。Skill 已经产生的 findings 仍然保留，sandbox error/timeout 会变成审计记录和人工复核项。输入、配置或数据库初始化失败才会终止，因为这些错误意味着评审没有可靠基础。

为什么 SQLite 还要抽象接口？

SQLite 适合 example、CLI 和 dry-run，接口让 Agent 不依赖具体数据库。真实多租户环境可以替换 SQL 后端，同时保留 task、decision、run、finding、artifact、report、metrics 的数据契约。

十三、诚实边界

  • 当前规则是 diff/hunk 启发式，不是完整 Go AST/SSA 分析。
  • staticcheck 仅支持 local-fallback；container 会拒绝该组合。
  • E2B runtime 是预留入口，当前返回 unsupported。
  • container 中运行 Go 检查需要 vendor/modules.txt。
  • 示例没有提供真实线上命中率、误报率或评审耗时数据，不应自行编造。

结语

tRPC-Agent-Go 提供的是 Agent 的运行基础设施：Tool、Skill、CodeExecutor、PermissionPolicy、Artifact、Event、Model 和 Telemetry。code_review_agent 在这些能力之上补齐了 diff 解析、Go 规则、SQLite schema、去重脱敏和报告生成，最终形成的是一条可测试、可隔离、可审计的代码评审链路，而不是一次不可回放的模型对话。
