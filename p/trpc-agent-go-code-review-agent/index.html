tRPC-Agent-Go 源码导读：如何构建一个可审计的 Go 自动代码评审 Agent

先读基础篇：《tRPC 基础与 tRPC-Agent-Go 关系：从 RPC 到 Agent 框架》。那一篇先把 RPC、tRPC 与 Agent 框架的关系讲清楚；本文只做一件事：从零开始把 examples/code_review_agent 这条代码评审链路按当前源码重新走一遍，重点回答“它到底怎么跑”“安全边界在哪里”“哪些能力来自框架，哪些是这个示例自己写的”。

本文基于 tRPC-Agent-Go 官方框架介绍和当前示例源码。最重要的纠偏先放在前面：

  1. 这不是一个让模型自由规划工具的 ReAct 自治 Agent。它是固定编排的 workflow：读输入、跑 Skill、可选跑沙箱、可选跑模型、写报告、落 SQLite。
  2. 正式规则入口不是 internal/review/parser.go。当前真实规则执行链是 skill_run -> scripts/check.sh -> check_rules.py/check_fallback.go。
  3. internal/review 里的 parser 仍然重要，但主要承担 diff 元数据、行号锚点、去重和脱敏等内部职责，而不是“正式规则入口”。
  4. --sandbox false 只是不跑 Go 检查，不会跳过 Skill 规则。真正只加载 Skill、不执行规则脚本的模式是 --mode dry-run。

如果你要在简历或面试中给它定位，建议说“自动代码评审 Agent 原型”，再立即补一句“当前实现是 Agent 框架托管的受控 workflow”。这样既没有抹掉 Runner、Skill、Tool、Model、事件和审计这些 Agent 框架能力，也不会把固定编排说成已经完成了自主规划型 Agent。

先把 PR、CR、diff、patch、hunk 说清楚

很多人一上来就说“我做了一个自动 CR Agent”，但术语如果混着用，后面源码很容易讲偏。

术语 这里的准确含义 在这个项目里对应什么
PR Pull Request。一次待合并的代码变更提案。 GitHub/GitLab 上的一次提交差异集合。
CR Code Review。对代码变更做检查、讨论和结论。 这个示例要自动化的就是 CR。
diff 两个版本之间的文本差异。 Agent 最终统一处理的是 unified diff。
patch diff 的一种常见分发形式。 gh pr diff --patch 导出的文件本质上还是 diff。
hunk diff 中按上下文切出来的一段改动块。 @@ -旧起点,旧行数 +新起点,新行数 @@ 开头的那一段。

例如：

1
2
3
4
5

diff --git a/config.go b/config.go
+++ b/config.go
@@ -1,2 +1,4 @@
 package foo
+const apiKey = "sk-1234567890abcdef"

这里：

  1. 整份文本是一个 diff。
  2. @@ -1,2 +1,4 @@ 是 hunk header：旧文件从第 1 行起取 2 行，新文件从第 1 行起取 4 行。
  3. +const apiKey = ... 是新增行。
  4. 行首 - 表示删除，行首空格表示未修改的上下文；这些前缀不是源代码本身。
  5. 如果这份 diff 来自某个 PR 页面下载的 .patch 文件，它依然是同一类输入。

后面整条 CR 链路，都是围绕“把各种来源的改动统一变成 diff，再针对新增行与 hunk 上下文做判断”展开的。

如果输入来自 GitHub PR，可以先导出 patch：

1

gh pr diff 2240 --repo trpc-group/trpc-agent-go --patch > /tmp/pr-2240.patch

这里 2240 是 PR 编号，--patch 要求输出 patch 格式，> 把终端输出重定向到本地文件。文件扩展名并不决定格式，后续 parser 真正读取的是文件内容。

这个项目一句话到底是什么

它不是“调用一个大模型帮我点评代码”。更准确的说法是：

这是一个面向 Go 代码变更的自动 CR workflow。输入可以是 diff 文件、PR patch、文件列表、Git 工作区或 fixture；系统先运行确定性 Skill 规则，再按权限进入隔离执行环境做可选 Go 检查，最后把 findings、权限决策、执行记录、报告和指标写入 SQLite，并保留可回放的审计轨迹。

这个表述里有三个关键词：

  1. workflow：阶段是固定的，不是模型现场决定下一步。
  2. deterministic：高置信规则优先，不把基础安全规则交给模型猜。
  3. auditable：不只要最终报告，还要知道哪些命令被允许、哪些被拒绝、哪些阶段被跳过。

先分层：哪些是框架层，哪些是 CR 业务层

理解这个示例最快的方法，不是从 main.go 一路往下翻，而是先把“tRPC-Agent-Go 提供的通用能力”和“这个示例自己实现的代码评审逻辑”拆开。

概念 在本文里的意思 主要落点
Skill 可复用工作流包，包含 SKILL.md、脚本入口和规则文档。 skills/code-review/
Tool Agent 受控调用的外部能力。 tool/skill、tool/codeexec
Runner 驱动一次 Agent 运行并消费事件流的执行壳。 Agent.Run、runner adapter
Event 运行过程中的阶段事件。 skill、sandbox、error、finish 等事件
CodeExecutor 真正执行脚本或命令的 runtime 抽象。 container、local-fallback、e2b
PermissionPolicy 工具真正执行前的白名单决策层。 internal/approval/gate.go
Artifact 报告、诊断文件等可回放产物。 JSON、Markdown、diagnostics
Telemetry 指标与 tracing，用来观察一次 review。 review trace、耗时、异常分布

上面这些是框架层或基于框架的通用执行边界。下面这些则是这个 CR 示例自己的业务层：

  1. internal/input：把多种输入统一成 diff。
  2. skills/code-review/scripts/*：正式规则入口脚本。
  3. internal/review：diff 元数据、脱敏、去重和 finding 数据结构。
  4. internal/llm：模型输入输出的合并与锚点校验。
  5. internal/storage/sqlite：默认 SQLite schema 与事务写入。
  6. internal/report：JSON 和 Markdown 报告生成。

面试时一定要分开说。否则很容易把“这个示例里有 SQLite”说成“tRPC-Agent-Go 框架默认内置 CR 数据库”。

它不是 ReAct 自治 Agent，而是固定工作流

这条纠偏非常关键。

很多人看到 Skill、Tool、Model，就会下意识把它讲成“模型先思考，再选择工具，再观察结果，再继续推理”。但当前 examples/code_review_agent 不是这个设计。它没有把“要不要跑哪个工具”交给模型现场决定，而是把阶段预先写死：

flowchart TD
    A[读取 CLI 请求] --> B[normalizeExecutionPlan]
    B --> C[input.Read 统一成 diff]
    C --> D[记录 running task]
    D --> E{mode == dry-run?}
    E -->|yes| F[只 load Skill，记录 skipped 审计]
    E -->|no| T{runtime == e2b?}
    T -->|yes| U[记录 unsupported，不执行 Skill]
    T -->|no| G[skill_load]
    G --> H[PermissionPolicy 审批 skill_run]
    H -->|allow| I[skill_run -> check.sh -> rule engine]
    H -->|non-allow| J[人工复核 warning]
    I --> K{sandbox requested?}
    J --> K
    K -->|yes| L[审批并执行 go test / go vet / staticcheck]
    K -->|no| M[跳过 sandbox]
    L --> N{model requested?}
    M --> N
    N -->|yes| O[发送脱敏 diff + 既有 findings 给模型]
    N -->|no| P[跳过 model]
    O --> Q[校验锚点、去重、合并]
    P --> R[生成报告]
    Q --> R
    F --> R
    U --> N
    R --> S[SQLite 事务写入 + Artifact + Telemetry]

这里的顺序由源码固定，不是模型临时规划出来的。所以更准确的叫法是：

  1. 这是一个 workflow agent。
  2. 模型是可选语义增强阶段，不是总调度器。
  3. 真正的“工具能不能执行”由 PermissionPolicy 和 executor 决定，不由模型一句话拍板。

Workflow、ReAct 与其他 Agent 形态

不要把 Agent 开发粗暴地分成“workflow 或 ReAct”两类。它们是最常见的两种组织方式，但不是全部：

形态 谁决定下一步 适合什么 当前示例是否属于它
固定 workflow 业务代码和状态机。 审计、CI、支付、审批等顺序稳定且需要可预测结果的流程。 是。
ReAct 模型根据当前观察结果在循环中选择 Tool。 调研、排障、开放式问答等步骤难预先写死的任务。 否。
图工作流 / 状态机 节点与分支预先定义，可有并行、重试和人工审批。 多阶段、长任务、需要恢复执行的系统。 可以作为当前 workflow 的演进方向。
多 Agent 协作 一个协调者把子任务交给不同 Agent。 角色和上下文可以清晰拆分的复杂任务。 否。
规划器 + 执行器 模型先生成计划，再由受控执行器逐步执行。 任务需要规划，但动作必须受权限和预算约束。 否。

后续若要演进成更复杂的 Agent，合理的方向不是先让模型拥有任意命令执行权，而是先保留 PermissionPolicy、沙箱、预算、超时和审计，再把“选择哪些低风险检查、何时请求人工复核、是否补充模型分析”做成受限决策。对 CR 这类安全敏感任务，固定 workflow 往往仍应保留为主路径。

输入变成 diff 后：internal/review 做什么

internal/review 不执行 secret-leak 或 http-body-close 规则。它负责把统一 diff 变成后续阶段都能使用的内部数据，并守住结果可信度：

  1. 定义 Finding、ParsedDiff、InputMetadata 等结构。
  2. 解析文件路径、语言、package、hunk、新增行及其新文件行号。
  3. 脱敏、生成 finding 去重键。
  4. 校验模型返回的 file/line 确实锚定到这次 diff 的新增行。

例如，假设下面三行位于 client.go 的一个合法 hunk 中，ParseUnifiedDiff 会把它们转为第 2、3、4 行的新增记录：

1

3

+resp, err := http.Get(url)
+if err != nil { return err }
+return use(resp.Body)

脚本随后才根据这些原始 diff 文本判断是否缺少 resp.Body.Close()。如果模型声称问题在 client.go:80，但本次 diff 只新增了第 2 至 4 行，模型结果会被拒绝并留下 model-invalid-anchor warning。internal/review 因此是“数据与可信边界”，不是第二套规则引擎；更完整的源码例子在后面的模型章节。

为什么要有 Shell、Python 和 Go fallback 三层

三者不是三套都要依次执行的规则，而是一条“稳定入口 + 优先实现 + 可用性降级”的链：

4

      -> check_fallback.go    # 没有 Python 时，执行等价的 Go fallback

check.sh 的意义是把“怎样运行规则”固定成一个小而稳定的协议：diff 从 stdin 写入临时文件，脚本再把 JSON 输出到 stdout。Agent 因此只需要批准并调用 scripts/check.sh，不需要关心宿主机是否安装 Python。

check_rules.py 是当前的主规则实现。它适合快速表达 diff 文本、正则、hunk 上下文和 JSON 输出这类规则，例如敏感信息、危险命令、明显的资源或 context 生命周期模式。

check_fallback.go 不是额外增加一次扫描，而是环境兼容兜底：当运行环境没有 python3 时，仍能运行同类规则并产出同一份 finding JSON 契约。最新源码还专门增加了两种运行时对 diff 路径解析一致性的测试，说明 fallback 必须与主实现保持行为对齐。

这也是为什么基础规则不直接交给 LLM：密钥泄露、危险命令等规则需要稳定、低成本、可重复测试，且每次运行应给出一致的 file、line、rule_id 和证据。LLM 的输出会随模型、提示词和上下文变化，更适合作为后面的语义补充，而不是安全规则的唯一裁判。

Issue 要求的规则，脚本怎样真正找到

是的，check.sh 最终会调用 Python 主实现或 Go fallback，由它们扫描 diff 中的新增代码。它们不是把变量放进运行时追踪，而是做固定的“模式 + 当前 hunk 上下文”检查：解析 +++ 和 @@ 后，得到文件和新文件行号；只看 + 新增行；某个模式命中后，再看同一 hunk 是否出现对应的清理或生命周期信号；最后 add_finding 写出 JSON 并按 (file, line, category, rule_id) 去重。

这正是在落实 Issue 对安全、并发、资源、错误处理、测试和数据库生命周期等规则类别的要求。Python 的规则函数与典型触发样例如下；Go fallback 用同一输入输出契约提供无 Python 环境的兼容实现。

规则为什么会误报或漏报

当前正式规则实现主要读取新增行和同一个 hunk 中的文本上下文。例如发现 os.Open 后，它会在当前改动块里寻找对应的 Close()；发现 context.WithCancel 后，会寻找 cancel 调用。

这种方法属于启发式检查：用可以快速验证的文本特征推断风险。它的优势是运行快、结果容易解释，也可以用 fixture 精确回归；边界则是它没有完整理解 Go 程序：

  1. **AST（抽象语法树）**会把源代码解析成函数、表达式、调用等语法节点，比文本匹配更清楚“这段代码是什么结构”。
  2. **SSA（静态单赋值）**等分析可以继续追踪变量值和控制流，更适合判断资源是否在其他分支关闭、错误是否跨函数传播。
  3. 当前 hunk 启发式看不到完整跨文件调用关系，因此可能把 hunk 外已经存在的清理逻辑漏掉，也可能因为同一 hunk 恰好出现某个关键词而错误地认为风险已处理。

testdata/fixtures 保存公开的固定输入和预期结果；testdata/holdout 则放独立或更具对抗性的样本，用来检查规则是否只“记住”了公开 fixture。面试时应把它称为可解释的第一层筛查，不能说成完整的 Go 静态分析器。可选模型能补充部分跨文件语义，但同样不能保证消灭误报和漏报。

Sandbox：真正的执行边界在哪里

规则命中只是第一层。这个示例还支持在权限允许时运行 Go 检查，例如 go test ./...、go vet ./...，以及可选 staticcheck ./...。

先把“沙箱”这个词说准确：沙箱不是某一种固定技术，而是一组执行约束，目标是让不完全信任的代码在受限环境中运行。Docker 容器是这里采用的具体实现之一；tRPC-Agent-Go 的 codeexecutor/container 负责创建和复用容器，示例自己的 internal/execution/exec.go 再把容器配置成当前的安全边界。local-fallback 则是开发回退，不等于同等级的隔离。

层级 作用

CodeExecutor / runtime 判定“让进以后在什么隔离环境里执行”

为什么在沙箱里跑 go test 和 go vet

两条命令检查的层次不同：

命令 主要作用 能发现什么
go test ./... 编译包并运行测试。 编译错误、测试失败、部分初始化和行为回归。
go vet ./... Go 官方静态分析器集合。 格式化字符串、不可达/可疑构造、锁和复制等常见问题。

它们和 Skill 脚本互补：脚本只拿到 diff，适合快速检查新增行的高置信规则；go test / go vet 需要真实仓库目录、go.mod、包依赖和完整代码上下文，才能编译和分析跨文件关系。它们的结果也要被记录成 sandbox_run，包括命令、退出码、耗时、输出摘要和失败状态。

为什么不直接在 check.sh 里执行 go test

因为两者的输入和风险不同：

  1. check.sh 的输入契约是 stdin 中的一份 diff，不保证旁边有完整仓库；go test 需要 repo workspace。
  2. check.sh 是 Skill 的规则执行入口，应该快速、确定、容易回归；测试和编译可能耗时、产生大量输出，甚至触发项目自定义生成逻辑。
  3. go test 可能执行被审仓库里的 init、测试代码或生成命令，必须先过 PermissionPolicy，再交给带超时、禁网、只读挂载和输出上限的 executor。
  4. 分开后可以单独回答“规则发现了什么”和“沙箱运行结果是什么”，失败时保留规则 findings，并把 sandbox 失败标成 needs_human_review。

所以正确的分工是：check.sh 做 diff 级确定性筛查，沙箱做需要完整工作区的编译、测试和静态检查；不是因为 Shell 不能启动 go test，而是不能绕过 Agent 的治理和审计边界。

什么时候必须提供被审仓库

只跑 Skill 规则时，输入可以只有 --diff-file、--fixture 或文件列表；脚本从 stdin 得到 diff，不需要访问完整仓库。开启 Go 沙箱检查时则不同：go test 和 go vet 需要 --repo-path 指向一个本地工作区，container executor 会把它只读挂载到 /workspace/repo。如果只提供 diff 而没有 --repo-path，代码不会猜一个目录，也不会执行宿主机检查，而是记录 sandbox-repo-required warning 和 skipped sandbox run。

所以你的理解是对的：diff-only 可以完成规则审查和可选模型审查；需要编译、测试或 Go 静态分析时，必须额外提供被审仓库。

什么时候会询问用户

这里要区分框架语义和当前 CLI 的实际行为。PermissionPolicy 可以返回 allow、deny 或 ask；当前示例的 internal/approval/gate.go 对固定的 skill_run、go test ./...、go vet ./...（以及显式开启的 staticcheck ./...）返回 allow，遇到不在 allowlist 的工具或命令返回 tool.AskPermission("unrecognized tool command requires human review")。

但当前 CLI 没有接入交互式审批 UI，所以不会真的暂停在终端等待你输入“是否执行”。ask 会被记录为 permission decision，相关 run 标记为 ask，结果增加 needs_human_review warning，然后跳过这条命令。若未来接 Web/API 审批，才可以把这个 decision 发给用户，用户批准后用同一个 task ID 恢复执行；拒绝则保留审计记录并结束或继续其他安全阶段。

PermissionPolicy 的三类决策和当前白名单

框架层的返回值有三类，含义不要混淆：

决策 白话含义 当前示例的实际情况
allow 这一次具体调用可以继续执行。 skill_run 只允许 scripts/check.sh；workspace_exec 只允许 go test ./...、go vet ./...；配置显式开启时再允许 staticcheck ./...；execute_code 只接受这些检查的内部 fallback 包装。
ask 策略无法确认安全，需要人工复核。 任何未知工具名、未知脚本、参数不匹配或命令变形都会走这里。当前 CLI 没有交互终端，所以记录后跳过。
deny 明确拒绝，不应执行。 当前策略对缺失的 permission request 直接 deny；普通的未知命令通常返回 ask，不是假装成 allow。

所以这里的“白名单”不是“所有 Shell 命令都能问用户后执行”，而是只把少数固定动作设为 allow。例如 go test ./... && curl ...、sh -c '...' 或用户把 check.sh 换成别的脚本，都不会因为看起来像测试而自动放行。当前 ask 结果会写入 SQLite 的 permission decision 和 needs_human_review warning；要实现真正的命令行或 Web 审批，需要增加 pending_approval 状态和审批接口，批准后重新校验 task、仓库 digest、命令摘要和过期时间，再从原 task 恢复，而不是在策略函数里直接放开任意命令。

当前运行时边界也要讲准：

  1. container 是正式隔离运行时，默认禁网、限制资源、只读挂载仓库。
  2. local-fallback 是本地回退运行时。
  3. e2b 当前是显式 unsupported 占位入口，不要说成已经支持远端沙箱。
  4. staticcheck 只允许 local-fallback，container 会拒绝该组合。
  5. 如果仓库没有 vendor/modules.txt，container 下的 go test / go vet 会记成 unsupported，而不是偷偷联网拉依赖。

Telemetry

Telemetry 更偏运行观测。这个示例会记录 review trace、耗时、工具调用数、异常计数、严重级别分布等指标。它回答的是“这次系统怎么跑的”，不是“报告正文是什么”。

SQLite

SQLite 是这个示例默认的审计存储，不是框架强制绑定；CLI 可以用 --no-persist 关闭持久化。它的价值在于把一次 review 拆成可查询的实体：

实体 具体记录什么 排障或审计时怎么用
task task ID、输入类型和引用、diff digest、仓库路径、模式、开始结束时间、状态。 查“这次评审审了什么、有没有完成”。
permission decisions 哪条命令申请执行、allow/ask/deny、原因和时间。 查“为什么脚本或 go vet 没有运行”。
filter decisions 某个过滤目标被允许、拒绝或要求人工复核的原因。 查治理策略是否按预期拦截。

findings severity、category、file、line、证据、修复建议、source、rule_id、置信度和状态。 查某个结论来自脚本、沙箱还是模型。
artifacts JSON/Markdown/diagnostics 文件的名称、路径、digest 和大小。 核对报告是否是这次任务生成的，是否被替换。

metrics 总耗时、沙箱/模型耗时、工具和模型调用次数、拦截数、严重级别与异常分布、脱敏次数。 查慢在哪里、误差主要来自哪个阶段、拦截是否异常。

写入时使用事务，目的不是为了“显得正规”，而是避免出现“报告文件已经生成，但数据库里只有半条 task 记录”这种审计断裂。

安全边界与失败降级是这篇文章最该记住的部分

如果只记住“它能发现 secret”，其实抓不到这个项目真正的工程价值。真正值得记的是安全边界和失败降级策略。

安全边界

  1. --skills-root 指向可信 Skill 安装目录，而不是被审仓库自带脚本目录。
  2. skill_run 和 workspace/code execution 都要过 PermissionPolicy。
  3. container runtime 默认禁网，降低源码和密钥外传风险。
  4. 证据、模型输入和错误文本会经过脱敏。
  5. 报告与 SQLite 只保存脱敏后的可回放信息。

失败降级

  1. Skill 被拒绝执行时，不是直接崩溃，而是转成 permission-non-allow 的人工复核项。
  2. sandbox 失败、超时或 unsupported 时，前面已有的 Skill findings 仍保留，不会整次 review 作废。
  3. model provider 出错时，会记录模型异常摘要，而不是把前面规则结果一起丢掉。
  4. dry-run 明确记录“因为模式原因跳过执行器”，不是静默什么都不干。

但并不是所有错误都会降级。输入读不到、模式组合非法、可信 Skill 根目录无效、报告无法写入或 SQLite 最终事务提交失败时，任务会返回错误，因为这时系统已经无法保证输入或审计结果完整。面试时可以概括为：可选检查失败尽量保留已有结果，基础契约和最终持久化失败则终止任务。

一句话：它追求的不是“所有阶段都必须成功”，而是“任何阶段失败都要留下可审计的解释，并尽量保留已经可靠得到的结果”。

按简历项目追问：面试官可能怎么问

下面的问题直接对应简历里的三条职责。回答时先讲结论，再给源码证据，最后说限制和取舍。

1. 你说“用了沙箱”，具体是怎么实现的？Docker 在这里扮演什么角色？

答：沙箱是执行安全边界，不是单独一种技术。这个项目的生产 runtime 是 Docker 容器，通过 trpc-agent-go/codeexecutor/container 创建容器；internal/execution/exec.go 配置 NetworkMode=none、非特权、丢弃 Linux capabilities、no-new-privileges、内存/CPU/PID 限制，并把被审仓库只读挂载到 /workspace/repo。命令在进入 executor 前还要经过 PermissionPolicy，并受到 timeout、输出上限和环境变量白名单约束。Docker 提供进程隔离，PermissionPolicy 和执行层共同组成沙箱治理；local-fallback 只是开发回退，e2b 在当前示例中仍是 unsupported 适配入口。

2. 为什么要在沙箱里运行 go test 和 go vet？

答：Skill 脚本只接收 diff，适合检查新增行的固定规则；go test ./... 需要完整 repo、模块依赖和包上下文，能发现编译错误、测试回归和运行时行为问题；go vet ./... 做 Go 常见静态分析。它们放进受限 runtime 是因为测试和 init 代码可能执行被审仓库中的逻辑，不能在宿主机直接运行。结果会以 sandbox run 记录命令、退出码、耗时、输出摘要和状态。

3. 为什么不把 go test 直接写进 check.sh？

答：不是 Shell 不能调用 Go，而是职责和安全边界不同。check.sh 的输入是 stdin diff，输出是规则 JSON；go test 需要 repo workspace，可能耗时、产生大量输出并执行仓库代码。把它放进脚本会绕开独立的 PermissionPolicy、runtime 选择、超时、禁网、只读挂载和 sandbox_run 审计。当前设计把 diff 筛查和工作区执行拆成两个可治理阶段。

4. 这个 code-review Skill 怎么设计，为什么不只写一个脚本？

答：我把它设计成一个可复用规则包：SKILL.md 定义角色、输入输出 JSON 契约和模型边界；rules.md 记录每个 rule_id 的触发条件、误报边界和 fixture；check.sh 是 Agent 唯一调用的稳定入口；check_rules.py 是主规则实现；check_fallback.go 是没有 Python 时的兼容实现。这样 runDirect 只需调用 scripts/check.sh，未来替换 Python 或增加 AST 检查器不影响编排代码；每条规则也可以用 fixture 单独回归。安全上，Skill 必须从可信 --skills-root 加载，不能执行被审仓库自带脚本。

具体执行时，check.sh 先执行 cat > "$tmp"，再用 command -v python3 选择 python3 check_rules.py "$tmp"，否则执行 GO111MODULE=off go run check_fallback.go "$tmp"。Python 规则在 if new_remaining > 0 and line.startswith("+") 分支只检查新增行，并通过 add_finding(...) 补齐 severity、file、line、evidence、rule_id 等字段；Go fallback 用 bufio.Scanner 解析相同的 +++ 文件头和 @@ hunk 计数，并用 finding struct 输出相同 JSON 契约。三者关系是“稳定入口 -> 主实现或环境降级”，不是三次重复扫描。

5. 你的规则引擎为什么不用 LLM 直接判断？

答：高置信安全规则需要稳定、低成本和可回归测试，例如 secret-leak、命令注入和 response body 未关闭。脚本能给出固定的 file、line、rule_id 和证据。LLM 更适合补充跨上下文语义，但有成本、隐私和误报波动，所以流程先跑 Skill 和沙箱，再把脱敏 diff、既有 findings 和执行摘要发给模型，最后对模型结果做新增行锚点校验和去重。

6. 你简历里写“LLM Agent”，模型实际上做了什么？

答：模型不是总调度器，也不决定是否执行高风险命令。它在固定 workflow 的 model_review 阶段接收脱敏后的完整 diff、脚本已有 findings、sandbox 摘要和治理摘要，返回增量 findings。程序会检查模型报告的 file/line 是否真实位于本次 diff 新增行，并合并去重；模型调用失败不会丢掉前面的确定性结果。

7. 为什么说这是 Agent 原型，而不是普通脚本？

答：普通脚本通常只负责检查和打印结果；这个原型实现了框架 agent.Agent 接口，并由 Runner 托管 session、request ID、Event 和生命周期，同时接入 Skill、Tool、PermissionPolicy、CodeExecutor、Model Provider、Artifact、Telemetry 和 SQLite。执行决策仍是固定 Workflow，所以我会称它为“Agent 框架托管的受控代码评审 Workflow”，不会说成已经完成自主 ReAct。

8. SQLite 里到底存了什么，为什么不是只保存最终报告？

答：task 保存输入引用、digest、模式和状态；permission/filter decisions 保存命令为什么允许、拒绝或要求人工复核；sandbox run 保存 runtime、退出码、耗时、超时和输出摘要；finding 保存结构化问题；artifact/report 保存报告文件引用和内容；metrics 保存总耗时、工具/模型调用、拦截数、严重级别和异常分布。它们在一次事务中关联提交，目的是支持按 task 回放“输入、决策、执行、结果”，而不是只知道最后一句结论。

9. 如果要把它演进成 ReAct 或图工作流，你会怎么做？

答：我会按“先图工作流、后受限 ReAct”的顺序演进，而不是直接把所有工具暴露给模型。

  1. 先把现有 runDirect 拆成有状态节点：input_loaded -> skill_run -> sandbox_run -> model_review -> report -> persist，每个节点写入 task 状态和输入/输出 digest，失败可从最近节点恢复。
  2. 把 go test、go vet、staticcheck、AST 分析和模型复核注册成带 schema 的 Tool，声明只读/联网/耗时/资源等级；模型只能从低风险、参数已校验的 Tool 中选择。
  3. 高风险动作继续由 PermissionPolicy 决定。ask 要进入审批 API，批准后带原 task ID 恢复，拒绝则写 decision 并继续安全分支；模型不能自行把 ask 变成 allow。
  4. 给规划循环加预算、最大步数、超时、重试退避和幂等键，避免模型重复跑测试或无限调用工具；每一步记录 Event、Telemetry 和 sandbox run。
  5. 最后再引入 ReAct，让模型根据已有 findings 决定“是否需要补充某个低风险检查”，但保留确定性规则作为必经主路径，并用 fixture/holdout 评估新增召回率和误报率。

这样演进后，图工作流负责可靠的阶段编排，受限 ReAct 负责有限的检查选择，Docker/PermissionPolicy/SQLite 这些安全和审计边界仍然不变。

10. 规则为什么只检查新增行和当前 hunk？

答：代码评审的目标是判断本次变更引入了什么风险，而不是重新扫描整个仓库。解析 @@ hunk header 可以得到新文件起始行号，脚本只在 + 行上报 finding，并把相邻上下文用于判断是否已有 Close、Unlock 或 cancel()。这样速度快、定位准确、容易回归；代价是看不到跨文件和 hunk 外的生命周期逻辑，所以它不是完整静态分析器。

11. secret-leak 规则会不会把示例字符串都报成密钥？

答：不会只靠变量名判断。should_report_secret 先匹配 token/私钥等形状；变量名命中后还要提取赋值字符串，检查长度，并过滤 placeholder pattern。命中后证据再经过 redact，所以 finding 可以保留“哪里疑似泄露”的信息，但报告和 SQLite 不保存明文密钥。规则仍是启发式，不能承诺 100% 召回。

12. defer Close 规则具体怎么判断？

答：例如新增 resp, err := http.Get(url) 后，reports_http_body_leak 会识别 HTTP 调用和变量名 resp，再在同一 hunk 文本中搜索 resp.Body.Close()；找不到就报 http-body-close。os.Open、sql.Open 和 BeginTx 分别走 resource_has_cleanup 或 database_has_cleanup，检查 Close / Rollback。它不是 Go 编译器级别的资源流分析，跨函数关闭可能被误判。

13. PermissionPolicy 的 allowlist 具体保护了什么？

答：internal/approval/gate.go 只允许精确匹配的 scripts/check.sh、go test ./...、go vet ./...，以及显式开启的 staticcheck ./...。命令参数、Tool 名称或 fallback code block 不匹配时返回 AskPermission。它防止模型或输入内容把执行器改成任意 Shell 命令，但不等于完整安全分析；容器隔离、超时、网络和输出限制仍然需要执行层提供。

14. 如果 go test 超时或容器没有 vendor 依赖，最终结论是什么？

答：不会把已有 Skill findings 丢掉。执行层会记录 timed_out 或 unsupported 的 sandbox run，生成 needs_human_review 项，并把 stderr digest、耗时和原因写入审计；最终报告会说明 Go 检查没有完成。基础输入无法读取、报告无法写入或 SQLite 事务提交失败则会终止任务，因为这些错误会破坏结果完整性。

15. 你如何证明这套规则没有“只记住公开样例”？

答：公开 testdata/fixtures 用于回归每条规则，testdata/holdout 保存未参与规则开发的变体和模型语义样本。测试会核对 rule_id、严重级别、状态、脱敏结果、去重和 sandbox 失败语义。进一步可以把 holdout 接入 CI，按规则类型统计召回率、误报率和模型增量 finding 的锚点通过率，而不是只看一次 demo 输出。

术语表

最后用一个紧凑版术语表收尾，方便回看：

术语 简明解释
Skill 一组可复用的规则文档、脚本和执行约束。
Tool Agent 可调用的受控能力接口。
Runner 驱动一次 Agent 执行并消费事件的外壳。
Event 运行过程中的阶段消息。
CodeExecutor 实际执行命令的 runtime 适配层。
PermissionPolicy 命令和工具调用的准入白名单。
Artifact 报告、诊断等可回放产物。
Telemetry trace、耗时、异常与分布指标。
Dedupe 对重复 finding 做稳定键去重。
Redaction 对 secret、token 等敏感文本做脱敏。
Unsupported 明确记录当前能力不可用，而不是静默失败。
Fixture 放在测试目录中的可重复输入样本。
Finding 一条结构化评审问题，包含位置、级别、证据和规则编号。
Provider 模型服务的接入实现，例如 fake、HTTP 或 OpenAI-compatible。
Runtime 命令实际运行的环境，例如 container 或 local-fallback。
Allowlist 只允许明确列出的命令或参数通过，即白名单。
stdin / stdout 进程的标准输入和标准输出；本例用它们传入 diff、返回 JSON。
Digest 内容摘要，常用于检查报告是否被替换。
Span 一段可追踪的运行区间，是 telemetry trace 的组成部分。
Anchor finding 对应的文件和新增行位置，即锚点。
Rollback 事务失败后撤销已写入的数据，避免只保存半条审计链。
AST 把代码表示为语法节点关系的抽象语法树。
SSA 便于追踪值和控制流的一种中间表示，常用于更深入静态分析。

结语

tRPC-Agent-Go 在这个示例里提供的不是“自动写 CR 结论”的魔法，而是一套把 Skill、Tool、PermissionPolicy、CodeExecutor、Artifact、Event、Telemetry 串起来的执行骨架。真正的 CR 价值来自这个示例自己补上的业务逻辑：输入收敛、正式规则脚本链、沙箱治理、模型锚点校验、脱敏去重和 SQLite 审计。

如果你要用一句话概括这篇源码导读，最准确的说法是：

这不是一个让模型自由发挥的代码评审机器人，而是一条以 Skill 规则为主、以权限和沙箱为边界、以 SQLite 和报告为回放载体的可审计 Go CR workflow。
