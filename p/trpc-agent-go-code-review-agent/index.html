tRPC-Agent-Go 源码导读：如何构建一个可审计的 Go 自动代码评审 Agent

先读基础篇：《tRPC 基础与 tRPC-Agent-Go 关系：从 RPC 到 Agent 框架》。那一篇先把 RPC、tRPC 与 Agent 框架的关系讲清楚；本文只做一件事：从零开始把 examples/code_review_agent 这条代码评审链路按当前源码重新走一遍，重点回答“它到底怎么跑”“安全边界在哪里”“哪些能力来自框架，哪些是这个示例自己写的”。

本文基于 tRPC-Agent-Go 官方框架介绍和当前示例源码。最重要的纠偏先放在前面：

  1. 这不是一个让模型自由规划工具的 ReAct 自治 Agent。它是固定编排的 workflow：读输入、跑 Skill、可选跑沙箱、可选跑模型、写报告、落 SQLite。
  2. 正式规则入口不是 internal/review/parser.go。当前真实规则执行链是 skill_run -> scripts/check.sh -> check_rules.py/check_fallback.go。
  3. internal/review 里的 parser 仍然重要，但主要承担 diff 元数据、行号锚点、去重和脱敏等内部职责，而不是“正式规则入口”。
  4. --sandbox false 只是不跑 Go 检查，不会跳过 Skill 规则。真正只加载 Skill、不执行规则脚本的模式是 --mode dry-run。

先把 PR、CR、diff、patch、hunk 说清楚

很多人一上来就说“我做了一个自动 CR Agent”，但术语如果混着用，后面源码很容易讲偏。

术语 这里的准确含义 在这个项目里对应什么
PR Pull Request。一次待合并的代码变更提案。 GitHub/GitLab 上的一次提交差异集合。
CR Code Review。对代码变更做检查、讨论和结论。 这个示例要自动化的就是 CR。
diff 两个版本之间的文本差异。 Agent 最终统一处理的是 unified diff。
patch diff 的一种常见分发形式。 gh pr diff --patch 导出的文件本质上还是 diff。
hunk diff 中按上下文切出来的一段改动块。 @@ -旧起点,旧行数 +新起点,新行数 @@ 开头的那一段。

例如：

1
2
3
4
5

diff --git a/config.go b/config.go
+++ b/config.go
@@ -1,2 +1,4 @@
 package foo
+const apiKey = "sk-1234567890abcdef"

这里：

  1. 整份文本是一个 diff。
  2. @@ -1,2 +1,4 @@ 是 hunk header：旧文件从第 1 行起取 2 行，新文件从第 1 行起取 4 行。
  3. +const apiKey = ... 是新增行。
  4. 行首 - 表示删除，行首空格表示未修改的上下文；这些前缀不是源代码本身。
  5. 如果这份 diff 来自某个 PR 页面下载的 .patch 文件，它依然是同一类输入。

后面整条 CR 链路，都是围绕“把各种来源的改动统一变成 diff，再针对新增行与 hunk 上下文做判断”展开的。

如果输入来自 GitHub PR，可以先导出 patch：

1

gh pr diff 2240 --repo trpc-group/trpc-agent-go --patch > /tmp/pr-2240.patch

这里 2240 是 PR 编号，--patch 要求输出 patch 格式，> 把终端输出重定向到本地文件。文件扩展名并不决定格式，后续 parser 真正读取的是文件内容。

这个项目一句话到底是什么

它不是“调用一个大模型帮我点评代码”。更准确的说法是：

这是一个面向 Go 代码变更的自动 CR workflow。输入可以是 diff 文件、PR patch、文件列表、Git 工作区或 fixture；系统先运行确定性 Skill 规则，再按权限进入隔离执行环境做可选 Go 检查，最后把 findings、权限决策、执行记录、报告和指标写入 SQLite，并保留可回放的审计轨迹。

这个表述里有三个关键词：

  1. workflow：阶段是固定的，不是模型现场决定下一步。
  2. deterministic：高置信规则优先，不把基础安全规则交给模型猜。
  3. auditable：不只要最终报告，还要知道哪些命令被允许、哪些被拒绝、哪些阶段被跳过。

先分层：哪些是框架层，哪些是 CR 业务层

理解这个示例最快的方法，不是从 main.go 一路往下翻，而是先把“tRPC-Agent-Go 提供的通用能力”和“这个示例自己实现的代码评审逻辑”拆开。

概念 在本文里的意思 主要落点
Skill 可复用工作流包，包含 SKILL.md、脚本入口和规则文档。 skills/code-review/
Tool Agent 受控调用的外部能力。 tool/skill、tool/codeexec
Runner 驱动一次 Agent 运行并消费事件流的执行壳。 Agent.Run、runner adapter
Event 运行过程中的阶段事件。 skill、sandbox、error、finish 等事件
CodeExecutor 真正执行脚本或命令的 runtime 抽象。 container、local-fallback、e2b
PermissionPolicy 工具真正执行前的白名单决策层。 internal/approval/gate.go
Artifact 报告、诊断文件等可回放产物。 JSON、Markdown、diagnostics
Telemetry 指标与 tracing，用来观察一次 review。 review trace、耗时、异常分布

上面这些是框架层或基于框架的通用执行边界。下面这些则是这个 CR 示例自己的业务层：

  1. internal/input：把多种输入统一成 diff。
  2. skills/code-review/scripts/*：正式规则入口脚本。
  3. internal/review：diff 元数据、脱敏、去重和 finding 数据结构。
  4. internal/llm：模型输入输出的合并与锚点校验。
  5. internal/storage/sqlite：默认 SQLite schema 与事务写入。
  6. internal/report：JSON 和 Markdown 报告生成。

面试时一定要分开说。否则很容易把“这个示例里有 SQLite”说成“tRPC-Agent-Go 框架默认内置 CR 数据库”。

它不是 ReAct 自治 Agent，而是固定工作流

这条纠偏非常关键。

很多人看到 Skill、Tool、Model，就会下意识把它讲成“模型先思考，再选择工具，再观察结果，再继续推理”。但当前 examples/code_review_agent 不是这个设计。它没有把“要不要跑哪个工具”交给模型现场决定，而是把阶段预先写死：

flowchart TD
    A[读取 CLI 请求] --> B[normalizeExecutionPlan]
    B --> C[input.Read 统一成 diff]
    C --> D[记录 running task]
    D --> E{mode == dry-run?}
    E -->|yes| F[只 load Skill，记录 skipped 审计]
    E -->|no| T{runtime == e2b?}
    T -->|yes| U[记录 unsupported，不执行 Skill]
    T -->|no| G[skill_load]
    G --> H[PermissionPolicy 审批 skill_run]
    H -->|allow| I[skill_run -> check.sh -> rule engine]
    H -->|non-allow| J[人工复核 warning]
    I --> K{sandbox requested?}
    J --> K
    K -->|yes| L[审批并执行 go test / go vet / staticcheck]
    K -->|no| M[跳过 sandbox]
    L --> N{model requested?}
    M --> N
    N -->|yes| O[发送脱敏 diff + 既有 findings 给模型]
    N -->|no| P[跳过 model]
    O --> Q[校验锚点、去重、合并]
    P --> R[生成报告]
    Q --> R
    F --> R
    U --> N
    R --> S[SQLite 事务写入 + Artifact + Telemetry]

这里的顺序由源码固定，不是模型临时规划出来的。所以更准确的叫法是：

  1. 这是一个 workflow agent。
  2. 模型是可选语义增强阶段，不是总调度器。
  3. 真正的“工具能不能执行”由 PermissionPolicy 和 executor 决定，不由模型一句话拍板。

Runner adapter 为什么只是外壳

internal/agent/runner_adapter.go 中的 reviewRunnerAgent 实现了框架的 agent.Agent 接口，但它没有让模型进入工具选择循环：

也就是说，下面这些输入最后都会被统一成一份 []byte 的 unified diff：

  1. 本地导出的 git diff 文件。

这一层的价值不是“会读文件”，而是把后面的规则、模型、报告和存储都建立在同一种输入契约上。

第三步：正式规则入口到底在哪里

这里必须说准。

很多讲解会把 internal/review/parser.go、internal/rules/rules.go 当成“规则正式入口”。但按照当前 Agent 的真实执行路径，正式规则入口是：

1
2
3
4

skill_run
  -> skills/code-review/scripts/check.sh
      -> python3 check_rules.py
      -> or GO111MODULE=off go run check_fallback.go

check.sh 的源码非常直接：

1
2
3
4
5

if command -v python3 >/dev/null 2>&1; then
  python3 "$script_dir/check_rules.py" "$tmp"
else
  GO111MODULE=off go run "$script_dir/check_fallback.go" "$tmp"
fi

也就是说：

  1. Agent 侧正式调用的是 skill_run。
  2. Skill 里固定暴露的稳定脚本入口是 scripts/check.sh。
  3. 真正跑规则时，优先走 Python 规则实现；没有 python3 再回退到 Go fallback。
  4. 所以“当前正式规则入口”应该表述成 skill_run -> check.sh -> check_rules.py/check_fallback.go。

仓库里虽然还有 internal/rules/rules.go，但当前主 Agent 路径没有调用 rules.Run；它目前主要由该包自己的测试覆盖。面试时可以说“仓库保留了 Go 规则实现和测试”，不能把它说成当前 CLI 的正式执行入口。

internal/review 在这条链里到底做什么

上面刚说过，internal/review 不是当前正式规则入口，但它绝不是“可有可无”。

它在当前源码里的核心职责更接近这四件事：

  1. 表达 Finding、ParsedDiff、InputMetadata 等内部数据结构。
  2. 解析 diff，提取文件路径、语言、package、hunk、新增行等元数据。
  3. 提供 RedactSecrets、去重键和公共清洗逻辑。
  4. 给模型结果做“你报的 file/line 是否真的锚定到本次 diff 新增行”这种验证。

所以一个准确说法是：

Skill 脚本链负责正式规则执行；internal/review 负责 Agent 内部的 diff 结构化、模型锚点校验、去重与脱敏。

这个区分非常重要，因为它直接决定你怎么解释“规则从哪里进”和“模型结果凭什么可信”。

规则为什么会误报或漏报

当前正式规则实现主要读取新增行和同一个 hunk 中的文本上下文。例如发现 os.Open 后，它会在当前改动块里寻找对应的 Close()；发现 context.WithCancel 后，会寻找 cancel 调用。

这种方法属于启发式检查：用可以快速验证的文本特征推断风险。它的优势是运行快、结果容易解释，也可以用 fixture 精确回归；边界则是它没有完整理解 Go 程序：

  1. **AST（抽象语法树）**会把源代码解析成函数、表达式、调用等语法节点，比文本匹配更清楚“这段代码是什么结构”。
  2. **SSA（静态单赋值）**等分析可以继续追踪变量值和控制流，更适合判断资源是否在其他分支关闭、错误是否跨函数传播。
  3. 当前 hunk 启发式看不到完整跨文件调用关系，因此可能把 hunk 外已经存在的清理逻辑漏掉，也可能因为同一 hunk 恰好出现某个关键词而错误地认为风险已处理。

testdata/fixtures 保存公开的固定输入和预期结果；testdata/holdout 则放独立或更具对抗性的样本，用来检查规则是否只“记住”了公开 fixture。面试时应把它称为可解释的第一层筛查，不能说成完整的 Go 静态分析器。可选模型能补充部分跨文件语义，但同样不能保证消灭误报和漏报。

这里特意保留了 --sandbox=false，因为它正好能说明一个经常被误解的点：这条命令仍会执行 Skill 规则。它只是明确告诉系统“不跑额外的 Go 沙箱检查，不跑模型”。

secret.diff 的核心内容是：

+++ b/config.go
@@ -1,2 +1,4 @@

这条命令背后的真实链路是：

  1. CLI 读取 --fixture secret.diff，由 input.Read 加载 testdata/fixtures/secret.diff。
  2. normalizeExecutionPlan 得到 mode=review、sandbox=false、model=false。
  3. runDirect 创建 task，先把任务写成 running。
  4. runSkillChecks 调用 skill_load。
  5. runSkillChecks 构造 skill_run 请求，命令固定为 scripts/check.sh，diff 通过 stdin 传入。
  6. PermissionPolicy 对 skill_run 做 allowlist 检查。
  7. check.sh 选择 check_rules.py 或 check_fallback.go 真正跑规则。
  8. 规则命中疑似密钥泄露，输出 secret-leak finding。
  9. stdout 被解析为结构化 findings；因为 sandbox=false，后续不跑 go test / go vet。
  10. 因为 model-enabled=false，后续不发模型请求。
  11. 系统写出 review_report.json、review_report.md、review_report.zh.md、review_diagnostics.json 和 SQLite 审计库。

这条链路里最值得记住的不是“发现了 secret”，而是：

  2. Skill 也受权限治理，不是“脚本天然可信”。
  3. 最终证据会脱敏，而不是把密钥明文复制到报告里。

再对比一下 dry-run，别把两个模式讲混

如果你改成：

go run ./cmd/review-agent \
  --fixture secret.diff \
  --mode dry-run \
  --runtime local-fallback \
  --skills-root ./skills \

真实语义是：

  1. 只验证 code-review Skill 能否加载。
  2. 不执行 skill_run。
  3. 不会产出那条真正的 secret-leak 规则 finding。
  4. 会留下 dry_run 的决策记录，以及 “Sandbox execution skipped by dry-run mode” 这类治理 warning。

所以：

  1. --sandbox false = 仍跑 Skill，只是不跑 Go 检查。
  2. --mode dry-run = 连 Skill 脚本都不执行，只验证加载与审计链路。

模式矩阵：到底哪些阶段会执行

下面这张表最适合面试和日常排错时快速对齐语义：

入口写法 Skill load Skill run Sandbox Go 检查 Model review 典型用途
默认 review 是 是 否，除非显式开启 否，除非显式开启 普通规则评审
review --sandbox=false --model-enabled=false 是 是 否 否 只跑确定性规则
review --sandbox --model-enabled=false 是 是 是 否 规则 + Go 检查
review --sandbox --model-enabled 是 是 是 是 完整链路

--mode rule-only 是 是 否 否 兼容别名

一句话总结：所有合法请求都会先读取输入并建立 task；dry-run 只 load Skill，e2b 当前在 Skill 前把规则/沙箱路径短路为 unsupported，其余 container/local-fallback 的 review 才进入 skill_load 和 skill_run。sandbox 与 model 再按 execution plan 决定是否追加；即使 e2b 的执行路径 unsupported，显式请求的 model 阶段仍可继续。

还有一个容易忽略的控制流：skill_run 被 PermissionPolicy 判为 non-allow 时会生成需要人工复核的 warning，但不会自动取消整个 execution plan。如果请求同时启用了 sandbox 或 model，后续阶段仍可能继续；最终报告会同时保留权限拒绝和其他阶段的结果。

Sandbox：真正的执行边界在哪里

规则命中只是第一层。这个示例还支持在权限允许时运行 Go 检查，例如 go test ./...、go vet ./...，以及可选 staticcheck ./...。

关键点在 internal/approval/gate.go 和 internal/agent/sandbox_step.go：

  1. 命令先经过 PermissionPolicy。
  2. 只有白名单命令才进入 executor。
  3. executor 再叠加 timeout、输出大小、环境变量白名单和 runtime 限制。

可以把它理解为两层门：

层级 作用
PermissionPolicy 判定“这条命令原则上让不让进”
CodeExecutor / runtime 判定“让进以后在什么隔离环境里执行”

当前运行时边界也要讲准：

  1. container 是正式隔离运行时，默认禁网、限制资源、只读挂载仓库。
  2. local-fallback 是本地回退运行时。
  3. e2b 当前是显式 unsupported 占位入口，不要说成已经支持远端沙箱。
  4. staticcheck 只允许 local-fallback，container 会拒绝该组合。
  5. 如果仓库没有 vendor/modules.txt，container 下的 go test / go vet 会记成 unsupported，而不是偷偷联网拉依赖。

模型阶段：模型拿到的不是未经处理的原始 diff

模型部分在 internal/llm/review.go。发送给 Provider 的输入是：

input := Input{
    DiffSummary:       review.RedactSecrets(string(diff)),
    InputMetadata:     inputMeta,

    SandboxSummary:    result.SandboxSummary,

这里要强调三点：

  1. DiffSummary 这个字段名容易误导：当前内容仍是脱敏后的完整 diff 文本，而不是重新概括出的自然语言摘要。
  2. 模型还会拿到既有 findings、sandbox 摘要和治理摘要，所以它做的是增量判断。
  3. 模型返回后不会直接进最终结论，还要经过 validateProviderFindings 校验 file/line 是否锚定到本次 diff 的新增行。

如果模型报了一个不在这次改动里的位置，系统不会照单全收，而是加一条 model-invalid-anchor 的人工复核 warning。这就是前面说的“internal/review 与相关 parser 负责模型锚点可信度”的真实落点。

去重、Artifact、Telemetry、SQLite 各自管什么

到这一步，很多讲解会只盯着 findings。但对真实 CR 系统来说，“怎么回放一次执行”同样重要。

Finding 去重

同一问题可能来自 Skill、模型或多个阶段，系统会按稳定 key 去重，避免同一 file/line/category/rule 被重复报。

Artifact

最终输出不只是一段终端文本，而是正式 Artifact，包括：

  1. review_report.json
  2. review_report.md
  3. review_report.zh.md
  4. review_diagnostics.json

它们会带上路径、digest、大小等信息，便于回放和核对。

Telemetry

Telemetry 更偏运行观测。这个示例会记录 review trace、耗时、工具调用数、异常计数、严重级别分布等指标。它回答的是“这次系统怎么跑的”，不是“报告正文是什么”。

SQLite

SQLite 是这个示例默认的审计存储，不是框架强制绑定；CLI 可以用 --no-persist 关闭持久化。它的价值在于把一次 review 拆成可查询的实体，例如：

  1. task
  2. permission decisions
  3. sandbox runs
  4. findings
  5. artifacts
  6. reports
  7. metrics

写入时使用事务，目的不是为了“显得正规”，而是避免出现“报告文件已经生成，但数据库里只有半条 task 记录”这种审计断裂。

安全边界与失败降级是这篇文章最该记住的部分

如果只记住“它能发现 secret”，其实抓不到这个项目真正的工程价值。真正值得记的是安全边界和失败降级策略。

安全边界

  1. --skills-root 指向可信 Skill 安装目录，而不是被审仓库自带脚本目录。
  2. skill_run 和 workspace/code execution 都要过 PermissionPolicy。
  3. container runtime 默认禁网，降低源码和密钥外传风险。
  4. 证据、模型输入和错误文本会经过脱敏。
  5. 报告与 SQLite 只保存脱敏后的可回放信息。

失败降级

  1. Skill 被拒绝执行时，不是直接崩溃，而是转成 permission-non-allow 的人工复核项。
  2. sandbox 失败、超时或 unsupported 时，前面已有的 Skill findings 仍保留，不会整次 review 作废。
  3. model provider 出错时，会记录模型异常摘要，而不是把前面规则结果一起丢掉。
  4. dry-run 明确记录“因为模式原因跳过执行器”，不是静默什么都不干。

但并不是所有错误都会降级。输入读不到、模式组合非法、可信 Skill 根目录无效、报告无法写入或 SQLite 最终事务提交失败时，任务会返回错误，因为这时系统已经无法保证输入或审计结果完整。面试时可以概括为：可选检查失败尽量保留已有结果，基础契约和最终持久化失败则终止任务。

一句话：它追求的不是“所有阶段都必须成功”，而是“任何阶段失败都要留下可审计的解释，并尽量保留已经可靠得到的结果”。

面试里最容易被追问的 8 个问题

1. 这个项目为什么不直接把 diff 发给模型？

因为高置信的安全、生命周期、资源关闭类问题适合先走确定性规则，而且模型不应该天然拥有执行命令的权力。这个项目先让 Skill 找稳定问题，再把模型放到后面做增量语义判断。

2. 为什么说它不是 ReAct Agent？

因为阶段顺序和工具调用是预定义的。模型没有在循环里自由决定“下一步跑哪个 Tool”，它只在可选 model review 阶段接收固定格式输入并返回增量 finding。

3. 当前正式规则入口在哪里？

准确答案是：skill_run -> scripts/check.sh -> check_rules.py/check_fallback.go。不要笼统说成“规则在 internal/review”。

4. internal/review/parser.go 还有什么用？

它负责 diff 的结构化、元数据、去重与脱敏，以及给模型 finding 做新增行锚点校验。它重要，但不是正式规则脚本入口。

5. --sandbox false 与 dry-run 的差别是什么？

--sandbox false 仍会跑 Skill 规则，只是关闭 Go 检查；dry-run 连 Skill 脚本都不执行，只验证 Skill 加载与审计链路。

6. 为什么 skill_run 自己也要 PermissionPolicy？

因为脚本本质上也是执行能力。不能因为脚本在仓库里，就把它当成天然可信、免审批的黑盒。

7. 模型为什么不能直接报任何 file/line？

因为系统会校验模型 finding 是否锚定在本次 diff 新增行。没有锚点的结果会被拒收，并转成人工复核 warning。

8. SQLite 在这里的作用是什么？

它不是为了“存个结果方便看”，而是为了把 task、权限决策、sandbox run、finding、artifact、report、metrics 关联成一条可回放审计链。

术语表

最后用一个紧凑版术语表收尾，方便回看：

术语 简明解释
Skill 一组可复用的规则文档、脚本和执行约束。
Tool Agent 可调用的受控能力接口。
Runner 驱动一次 Agent 执行并消费事件的外壳。
Event 运行过程中的阶段消息。
CodeExecutor 实际执行命令的 runtime 适配层。
PermissionPolicy 命令和工具调用的准入白名单。
Artifact 报告、诊断等可回放产物。
Telemetry trace、耗时、异常与分布指标。
Dedupe 对重复 finding 做稳定键去重。
Redaction 对 secret、token 等敏感文本做脱敏。
Unsupported 明确记录当前能力不可用，而不是静默失败。
Fixture 放在测试目录中的可重复输入样本。
Finding 一条结构化评审问题，包含位置、级别、证据和规则编号。
Provider 模型服务的接入实现，例如 fake、HTTP 或 OpenAI-compatible。
Runtime 命令实际运行的环境，例如 container 或 local-fallback。
Allowlist 只允许明确列出的命令或参数通过，即白名单。
stdin / stdout 进程的标准输入和标准输出；本例用它们传入 diff、返回 JSON。
Digest 内容摘要，常用于检查报告是否被替换。
Span 一段可追踪的运行区间，是 telemetry trace 的组成部分。
Anchor finding 对应的文件和新增行位置，即锚点。
Rollback 事务失败后撤销已写入的数据，避免只保存半条审计链。
AST 把代码表示为语法节点关系的抽象语法树。
SSA 便于追踪值和控制流的一种中间表示，常用于更深入静态分析。

结语

tRPC-Agent-Go 在这个示例里提供的不是“自动写 CR 结论”的魔法，而是一套把 Skill、Tool、PermissionPolicy、CodeExecutor、Artifact、Event、Telemetry 串起来的执行骨架。真正的 CR 价值来自这个示例自己补上的业务逻辑：输入收敛、正式规则脚本链、沙箱治理、模型锚点校验、脱敏去重和 SQLite 审计。

如果你要用一句话概括这篇源码导读，最准确的说法是：

这不是一个让模型自由发挥的代码评审机器人，而是一条以 Skill 规则为主、以权限和沙箱为边界、以 SQLite 和报告为回放载体的可审计 Go CR workflow。
