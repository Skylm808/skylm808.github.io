Codex CLI 源码导读（十一）：一项任务怎样从输入走到验证

前十篇把 Codex 的会话、上下文、工具、权限、MCP、扩展、多 Agent 和界面拆开讲。这一篇不再追源码，而是把它们放回一项真实任务：用户给出一句要求，Codex 了解工作区、修改文件、验证结果，然后在该停的时候停下。

我们先用本系列所在的 Hugo 博客做例子，再看同一套方法怎样用于修改 Go 代码。读完这一篇，应该能回答三个问题：怎样把任务说清楚？Codex 在每一步实际会用什么工具？为什么“构建通过”后还不能擅自提交或发布？

先给 Codex 一项说得清楚的任务

假设用户输入：

1
2
3

在 content/post/ai/ 新增一篇文章，介绍如何为 Hugo 博客写文章。
参考相邻文章的文件名和 front matter；不要改动已有文章；
完成后验证站点可以构建，只汇报结果，不要提交、推送或发布。

这不是一句“帮我写篇博客”的泛泛要求。它已经给出了五类信息：

用户给出的信息 Codex 据此确认的完成条件
目标 新增一篇面向博客读者的文章。
位置 文件应在 content/post/ai/。
约定 文件名和 front matter 要参考相邻文章。
验证 Hugo 必须能渲染站点。
边界 不修改既有文章，不提交、不推送、不发布。

把目标、范围、验证和禁止动作写进输入，Codex 才能判断何时完成。否则它只能猜测“写好”是什么意思，也无法知道是否该继续提交或部署。

这一次任务里会反复出现的词

不必先背定义，只要把它们放到这次任务中理解：

名词 在本例中的意思
Thread 这段持续对话，保存用户的要求、工具结果和最终回复。
Turn 用户提交这条任务后，由这条输入触发的一段连续工作。
上下文 Codex 当前已经掌握的证据，例如项目规则、相邻文章、Git 状态和构建输出。
工具 搜索、读取、编辑文件和运行命令的能力。模型提出下一步，工具在本机实际执行。
验证 用命令输出和文件差异证明完成条件，而不是凭“看起来没问题”结束。

模型决定下一步值得做什么；Codex 在已有权限范围内执行这一步、记录结果并展示给用户。模型不会自动拥有整个仓库、网络或发布权限。

一次任务的全貌 

flowchart LR
    A["用户给出目标和边界"] --> B["理解完成条件"]
    B --> C["搜索并读取必要材料"]
    C --> D["检查 Git 状态"]
    D --> E["精确修改文件"]
    E --> F["运行对应验证"]
    F --> G{"验证通过？"}
    G -- "否" --> H["读取报错，修正后重试"]
    H --> F
    G -- "是" --> I["检查差异和范围"]
    I --> J["汇报并结束"]

    P["权限与审批"] -.约束每一步.-> C
    P -.约束每一步.-> E
    P -.约束每一步.-> F

下面按这条顺序走一遍。工具的输出会进入下一步的上下文，所以这不是一份预先写死的命令清单：读到什么、构建是否失败，都会改变后续动作。

1. 先找规则和材料，而不是立刻写文章

进入陌生仓库时，Codex 不会假定自己知道目录结构或写作约定。它先需要回答几个具体问题：站点如何识别文章？同系列文章放在哪里？工作区里是否已有用户的未提交改动？

此时常见的动作如下：

1
2
3
4

rg --files -g 'AGENTS.md' -g 'hugo.yaml' -g '*.md'
sed -n '1,100p' hugo.yaml
sed -n '1,80p' content/post/ai/codex-cli-agent-architecture-10.md
git status --short

rg：先定位，不靠猜路径

rg 是 ripgrep 的命令名，它是用 Rust 编写的快速文本搜索工具。rg --files 列出受 Git 忽略规则影响的文件；带上关键词时，它可以找出某个配置项、标题、函数名或测试名出现的位置。

这里用它寻找 AGENTS.md、hugo.yaml 和文章文件，不是为了把整个仓库都读一遍，而是为了先定位值得读取的少量文件。比如找到相邻的第十篇文章后，才知道应该从哪份 front matter 参考格式。

sed：只看当前需要的一段

sed 是文本流编辑器。sed -n '1,80p' <文件> 在这里并不修改文件，而是只输出前 80 行。对 Hugo 文章来说，开头通常就能看到标题、日期、分类、标签和正文结构；对源代码来说，它也适合读取命中搜索结果附近的函数。

限制读取范围有两个好处：输出更容易检查，也不会让无关内容淹没当前任务。若前 80 行不够，再按需要扩展范围即可。

git status --short：先保护用户已有的工作

这个命令用紧凑格式列出已修改和未跟踪的文件。它不是“提交前才需要”的命令，而是修改前就应收集的上下文：若列表里已有用户正在编辑的文章，Codex 不能为了获得干净工作区而还原、删除或覆盖它。

从这些材料中，Codex 可以得出一个明确结论：Hugo 文章需要由 +++ 包住的 TOML front matter，新的内容应放在 content/post/ai/，并且后续只能触及任务所需的文件。

2. 再把文章写到明确的范围里

现在才创建新文件，例如：

1

content/post/ai/how-to-write-hugo-post.md

一篇文章至少有两层内容：正文，以及开头的 front matter。front matter 是 Hugo 用来组织页面的元数据；本仓库使用 TOML 语法，通常会包含日期、标题、slug、分类和标签。参考相邻文章，不表示复制它的正文，而是复用仓库已经采用的文件结构和写作约定。

apply_patch：用补丁表达精确改动

apply_patch 是 Codex 的文件编辑工具。它用“新增这一段、替换这几行、删除这部分”的补丁描述修改，而不是让 Shell 把整份文件重定向覆盖。对于新增 Markdown，它可以明确创建一个文件；对于已有文件，它会根据补丁附近的原文确认修改位置。

它的意义不是要求读者在终端手写补丁，而是让改动范围可见、可检查。若任务只要求新增文章，补丁不应顺手改主题配置、相邻文章或生成目录。写入前，Codex 还会按当前的工作区权限检查这项操作能否执行；超出可写范围、需要联网或副作用更大的动作可能需要审批，或直接被拒绝。

3. 用 Hugo 验证文章，而不是只检查 Markdown 外观

文章能够打开，不代表站点一定能渲染。错误的日期格式、遗漏的 front matter 分隔符、模板不接受的字段，都可能在构建时才暴露。

1

hugo --renderToMemory

hugo 是静态站点生成器。--renderToMemory 要求它完成渲染检查，但不把生成页面写进发布目录，适合验证内容改动。退出状态为 0 表示当前站点可以由这套本地配置渲染；失败时，错误输出通常会给出文件名、行号或无法解析的字段。

若命令失败，正确的下一步不是报“失败”就结束，也不是盲目重跑，而是读取报错、定位到文章或配置、修正后再次运行。验证结果是下一步选择的证据。

4. 构建成功后，还要看改了什么

Hugo 构建成功只能证明站点能渲染，不能证明 Codex 只改了预期文件。因此最后还要检查差异：

1
2
3

git diff --check
git status --short
git diff -- content/post/ai/how-to-write-hugo-post.md

git diff --check 检查已跟踪改动中的常见空白错误；git status --short 再次列出新文件和原有改动；git diff -- <路径> 让人或 Codex 聚焦某个文件的实际差异。新建且尚未跟踪的文件不会出现在普通 git diff 中，需要直接读取它，或使用 git diff --no-index --check /dev/null <新文件> 检查空白格式。后一个命令发现两份文件不同可能返回 1，因此要看输出中是否有格式错误，不能把任何非零状态都误判为失败。

这时可以得到几类不同的证据：

证据 能证明什么 不能证明什么
新文件位于目标目录 修改位置正确 正文技术事实完全正确
front matter 与相邻文章一致 Hugo 能按仓库约定识别文章 远程部署会成功
hugo --renderToMemory 成功 当前站点可以渲染 远程发布已完成
差异和 Git 状态符合预期 没有擅自清理或扩大改动范围 改动已经提交

5. 把结果交还给用户，然后停止

最终回复不必复述全部命令，但应交代改动、验证和边界：

已新增 content/post/ai/how-to-write-hugo-post.md，并沿用现有文章的 TOML front matter。hugo --renderToMemory 已通过，差异检查未发现空白错误。原有未提交改动仍保留；未执行提交、推送或发布。

“未执行提交、推送或发布”不是多余的客套话。构建通过只完成了用户要求的本地验证；提交、推送和部署会改变版本历史或远程环境，属于需要明确授权的下一步。达到完成条件后停止，是可靠工作流的一部分。

换成修改 Go 代码，流程还一样吗？

核心流程完全一样：明确目标和边界，先读证据，再做最小改动，用与任务相符的验证检查结果，最后确认差异并汇报。不同的是，文章的主要证据是 Hugo 渲染，而代码的主要证据是行为测试。

例如，用户提出：

1
2
3

修复用户注册时空邮箱没有被拒绝的问题。
先阅读现有测试和校验逻辑；补充回归测试；只修改相关 Go 包；
运行受影响包的测试，不要提交。

对应的动作会变成：

Hugo 写文章 Go 修复问题
rg 找相邻文章和配置 rg 找注册逻辑、错误文案和相关测试
sed 读取 front matter 和文章结构 sed 读取测试、目标函数和调用方附近的代码
apply_patch 新增 Markdown apply_patch 修改实现，并新增或更新回归测试
hugo --renderToMemory 检查渲染 go test ./目标包 检查行为
检查文章差异和 Git 状态 检查实现、测试和 Git 状态是否都在预期范围

Go 的例子还会多两个常用命令：

1
2

gofmt -w path/to/file.go
go test ./path/to/package

gofmt 是 Go 的标准格式化工具。它解决的是代码排版一致性，不证明功能正确；go test 执行测试并给出行为证据。通常应先跑受影响包，既能快速定位失败，也避免无关测试拖慢反馈；若项目规则或改动范围要求，再扩大到更多包或整个仓库。

对 Go 代码而言，“补充回归测试”尤其重要：测试应先能表达空邮箱被拒绝这个预期，再由实现改动让它通过。这样验证的不是“代码看起来合理”，而是用户报告的具体问题不会再次出现。

用同一条原则结束整个系列

无论是写一篇 Hugo 文章，还是修一处 Go 代码，Codex 的工作方式都不是自动连续地产生改动。它应在每一步收集证据，并让证据决定下一步：

  1. 说清目标、范围、验证方式和禁止动作。
  2. 先搜索和读取必要材料，确认项目约定与已有状态。
  3. 用小而明确的补丁完成改动。
  4. 运行与任务类型对应的验证；失败就根据输出修正并重试。
  5. 检查最终差异，报告结果与未执行的外部动作，然后结束。

这就是前十篇里 Thread、上下文、工具、权限和事件在日常任务中的共同位置：它们不是需要分别记住的名词，而是让一次改动可控、可验证、可交还给用户的条件。
