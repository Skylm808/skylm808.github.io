阅读时长: 21 分钟

从 HTTP、Dubbo2、gRPC、Triple 到高并发：读懂 Pixiu 网关的协议与治理代码

很多人问“网关怎样扛高并发”，答案很容易变成一串词：连接池、限流、熔断、负载均衡。

但把这些词背出来不等于理解网关。更重要的问题是：请求以什么协议进入，Pixiu 在哪里转换，慢请求和故障又在哪一层被挡住。 本文结合 dubbo-go-pixiu 当前源码，先把 HTTP、Dubbo2、gRPC、Triple 讲清楚，再沿一条请求链路看 Pixiu 已经落地的高并发保护。

文中源码路径均相对于仓库根目录 dubbo-go-pixiu。

0. 先把高频术语翻译成人话

读网关源码时，最容易混淆的是“请求”“资源”“连接”和“上下文”这几组词。先建立一个共同词典：

术语 在 Pixiu 里的含义 可以把它想成
listener 监听端口并接收某一种协议 大楼入口
filter chain 按顺序执行的一组过滤器 入口安检流水线
route 根据 path、method 找到 cluster 的规则 分诊台
cluster 一组同类上游 endpoint 的逻辑集合 库存服务这个“服务池”
endpoint cluster 中一个具体地址 10.0.0.11:8080 这台实例
resource Sentinel 统计和治理的逻辑资源名 /inventory/* 这条业务车道
HttpContext Pixiu 保存一次 HTTP 请求状态的对象 本次请求的工作台
context.Context Go 里传播取消、deadline 和少量元数据的值 请求的截止时间/取消信号

因此，“对库存接口限流”不是对一个抽象的网关总开关限流，而是先把 URL 匹配成某个 Sentinel resource，再对这个 resource 计算流量；“连接池”也不是 endpoint 池，前者复用 TCP/HTTP 连接，后者是服务实例地址集合。

本文后面还会出现几组性能术语：QPS 是每秒请求数，P95/P99 是把请求耗时从小到大排序后位于 95%/99% 位置的延迟，表示“绝大多数请求”和“尾部慢请求”有多慢；goroutine 是 Go 的轻量并发执行单元，GC 是垃圾回收，过多临时对象会增加 GC 工作；deadline 是请求必须完成的绝对截止时间，timeout 通常是从现在开始计算的一段最长等待时间；idempotent（幂等）表示同一个请求执行一次或多次，业务最终结果应该相同，例如按 ID 查询通常幂等，扣款通常不天然幂等。

1. 先给结论：四种协议不是同一层的东西

名称 主要定位 典型传输与编码 最适合的场景
HTTP/REST 通用 Web API 风格 HTTP/1.1 或 HTTP/2，常用 JSON 浏览器、开放平台、调试友好的 API
Dubbo2 Dubbo 传统 RPC 协议 TCP 二进制协议，常见 Hessian2 已有 Dubbo2 服务的内部 RPC
gRPC 标准化、多语言 RPC 框架 HTTP/2 + Protobuf 强类型内部服务、四种流式调用
Triple Dubbo 3 的云原生 RPC 协议 HTTP/2 + Protobuf，带 Dubbo 语义 Dubbo 服务治理与 HTTP/2/多语言互通并存

HTTP 更像一套通用的 Web 交互语义；Dubbo2、gRPC、Triple 都是 RPC 调用方式。它们都能完成“调用远端的一个方法”，但报文格式、服务发现与治理语义不同。

以“查询用户 42”为例：

1
2
3
4

HTTP:   GET /users/42
Dubbo2: 调用 com.example.UserService.GetUser(42)，按 Dubbo 二进制协议编码
gRPC:   调用 /example.UserService/GetUser，HTTP/2 承载 Protobuf 消息
Triple: 调用 Dubbo 服务/方法，经 HTTP/2 + Protobuf 传输，并携带 tri-* 元数据

1.1 HTTP：人和生态最容易理解的入口

HTTP 的优势不是“性能一定最高”，而是几乎所有客户端都理解它：浏览器、curl、CDN、API 网关、各种语言 SDK。JSON 也便于排查。

例如：

1
2
3

GET /users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer <token>

代价是 JSON 编解码和文本头部通常比 Protobuf 更大；HTTP 本身也没有替你定义“接口方法、参数类型、重试语义”。这些需要 REST 规范、OpenAPI 或网关配置补齐。

1.2 Dubbo2：传统 Dubbo RPC，不是 HTTP

Dubbo2 常见于 Java/Dubbo 体系。调用方不拼 URL，而是声明接口、方法、参数类型和参数值；协议在 TCP 上使用二进制帧，传统默认序列化常见 Hessian2。

1

userService.getUser(42)

对业务开发者它像本地方法调用，对网络而言却是 RPC。服务接口、版本、分组、注册中心和负载均衡等都是 Dubbo 治理体系的一部分。

Pixiu 的网络 Dubbo 入口由 pkg/filter/network/dubboproxy/manager.go 处理：它解码 Dubbo 调用，按 Dubbo attachment 中的服务路径和方法路由，再把调用交给后续 Dubbo filter。向下游发起传统 Dubbo 调用时，pkg/filter/network/dubboproxy/filter/proxy/proxyfilter.go 构造带 Hessian2 和 generic 调用配置的 Dubbo URL。

1.3 gRPC：HTTP/2 上的强契约 RPC

gRPC 通常以 .proto 描述接口和消息，编译生成多语言客户端。它使用 HTTP/2，多路复用使一条连接可并行承载多个 stream，并原生定义四种调用方式：一元、客户端流、服务端流、双向流。

1
2
3

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}

1

/example.UserService/GetUser

这里的路径不是 REST 资源 URL，而是服务和方法标识。Protobuf 的二进制表示通常更紧凑；代价是抓包可读性较低，接口变更要遵守 Protobuf 的兼容规则。

Pixiu 的原生 gRPC listener 在 pkg/listener/grpc/grpc_listener.go。它用 Go gRPC 的 UnknownServiceHandler 接住未知服务，把收到的 ServerStream 连同完整方法名送到网络 filter chain。新的流式代理实现在 pkg/filter/network/grpcproxy：它向选中的 endpoint 建立出站 gRPC stream，并在上下游之间双向转发。

1.4 Triple：不是“换了名字的 gRPC”

Triple 和 gRPC 的共同点很明显：都站在 HTTP/2 与 Protobuf 生态上，都适合高性能 RPC 与流式通信。但它们不是同一个协议实现。

Triple 是 Dubbo 3 的协议，保留 Dubbo 的服务治理语义。例如 Pixiu 的 gRPC proxy 协议辅助代码会识别 tri- 前缀的元数据，像 tri-service-version、tri-service-group；位置在 pkg/filter/network/grpcproxy/filter/proxy/protocol.go。这些信息对应 Dubbo 服务的版本、分组等概念，而不是普通 gRPC 的必备头。

Pixiu 的 Triple listener 在 pkg/listener/triple/triple_listener.go 中创建 Dubbo-go 的 Triple server，并以 proxy mode 收到调用。后续通常进入 Dubbo proxy connection manager 的 OnTripleData，与 Dubbo2 一样按接口和方法路由，再由配置决定出站是 Dubbo2 还是 Triple。

因此更准确的说法是：gRPC 是标准 RPC 框架；Triple 是 Dubbo 3 在 HTTP/2/Protobuf 基础上实现的 RPC 协议，并把 Dubbo 服务治理语义带进来。

1.5 序列化到底解决什么问题

业务代码里的对象不能直接放进网络。比如 Go 里有一个请求对象：

1
2
3

type GetUserRequest struct {
    ID int64
}

发送前要把它转换成字节，接收方再把字节还原成对象，这个过程分别叫序列化（serialize）和反序列化（deserialize）。序列化格式决定了几个实际问题：

  1. 网络上传多少字节，影响带宽和延迟；
  2. 编解码要消耗多少 CPU 和内存；
  3. 不同语言能不能准确理解同一份消息；
  4. 服务升级后，旧客户端和新服务能不能继续通信。

JSON、Protobuf、Hessian2 都是序列化格式，但定位不同。JSON 便于人读，适合开放 HTTP API；Protobuf 和 Hessian2 都是二进制格式，更适合 RPC 内部传输。二进制不等于一定更快，最终还要看消息大小、生成代码、反射、压缩和业务负载。

1.6 gRPC/Protobuf 与 Hessian2 的区别

先纠正一个常见说法：gRPC 不是一种序列化格式。 gRPC 是 RPC 框架和调用模型，通常使用 HTTP/2 传输；在 gRPC 中，真正把请求对象编码成字节的默认格式是 Protobuf。Hessian2 则是 Dubbo 生态常用的对象序列化格式，通常放在 Dubbo/Dubbo generic invocation 的协议帧里。

对比项 gRPC + Protobuf Dubbo2 + Hessian2
分层 gRPC 负责 RPC 调用，HTTP/2 负责传输，Protobuf 负责消息编码 Dubbo 协议负责 RPC 帧，Hessian2 负责参数/返回值编码
数据模型 .proto 明确定义 message、字段编号和类型，常由代码生成 以对象/参数类型为中心，编码中可携带类型信息，动态 generic 调用更方便
性能特征 二进制、字段 tag 紧凑，生成代码路径通常稳定可预测 二进制、对 Dubbo 对象调用友好，但动态类型和对象图会带来额外编码成本
跨语言 Protobuf 生态覆盖 Go、Java、C++、Python 等，契约一致 主要服务于 Dubbo 生态，跨语言要确认对应 Hessian2 实现与类型兼容
演进方式 通过字段编号和兼容规则演进，旧客户端通常可忽略未知字段 依赖双方类型名、字段和序列化实现的兼容，升级前要验证对象结构
常见场景 强契约内部 API、流式调用、多语言微服务 Dubbo2 传统服务、泛化调用、需要传递 Dubbo 对象参数的场景

用同一个 GetUserRequest{ID: 42} 举例：

1

4

gRPC + Protobuf:
  .proto 定义 GetUserRequest.id = 1
  -> 生成的 protobuf 编码器把字段编号和值写成二进制
  -> gRPC 将这条 message 放入 HTTP/2 stream

Dubbo2 + Hessian2:
  Dubbo invocation 声明接口、方法和参数类型
  -> Hessian2 将参数对象/类型信息编码成二进制
  -> Dubbo 将它放进请求帧发送给 provider

两者都能减少 JSON 的文本体积，但优化方向不完全一样：Protobuf 强调稳定的 schema 和跨语言契约，Hessian2 更贴近 Dubbo 的对象调用与泛化调用。需要在浏览器和 RPC 服务之间转换时，网关还要承担一次反序列化和再序列化，例如 Pixiu 的 pkg/filter/http/grpcproxy/grpc.go 用 jsonToProtoMsg 把 HTTP JSON 变成动态 Protobuf，再用 protoMsgToJson 把响应转回 JSON；这会产生 CPU、内存和延迟成本。

1.7 序列化格式怎么选，以及 Pixiu 当前代码的边界

可以按下面的决策思路选：

  • 对外 HTTP API：JSON 可读、调试和浏览器兼容性最好；即使内部下游是 gRPC，也可以由 Pixiu 做 JSON/Protobuf 转换。
  • 新建的跨语言内部 RPC：优先考虑 gRPC + Protobuf，接口契约、生成代码和兼容性工具比较完整。
  • 已有 Dubbo2 服务：通常保持 Dubbo + Hessian2，避免为了换编码格式同时改造 provider、consumer 和注册治理。
  • 泛化调用或动态参数：Hessian2 在 Dubbo generic invocation 场景更自然，但要用真实对象大小和类型复杂度做基准测试。

还要区分“协议理论上支持什么”和“当前 Pixiu 代码实际配置了什么”。本仓库中：

  • pkg/filter/network/dubboproxy/filter/proxy/proxyfilter.go 的 Dubbo 和 Triple 出站示例都显式设置 SerializationKey 为 Hessian2；
  • pkg/listener/triple/triple_listener.go 创建 Triple server 时显式使用 WithCodecType(tripleConstant.HessianCodecName)；
  • pkg/filter/http/grpcproxy/grpc.go 的 HTTP 到 gRPC 转换使用 Protobuf message 和 descriptor；
  • pkg/client/dubbo/dubbo.go 会读取 effective serialization，配置可以明确选择 hessian2 或其他 Dubbo-go 支持的序列化方式。

所以文章里说“Triple 基于 HTTP/2/Protobuf 生态”描述的是 Triple 的互通方向；而在当前这份 Pixiu 实现中，具体 listener/proxy 仍可能使用 Hessian codec。排查线上报文时，应以 listener、filter 和 client 的实际配置为准，不能只根据协议名称推断序列化格式。

2. Pixiu 如何把不同协议接进同一个网关

Pixiu 不是要求所有业务统一成一种协议，而是为不同入口准备 listener，再让路由和 filter 决定如何调用下游。

flowchart LR
    H[HTTP / JSON Client] --> HL[HTTP listener]
    D[Dubbo2 Client] --> DL[TCP / Dubbo listener]
    G[gRPC Client] --> GL[gRPC listener]
    T[Triple Client] --> TL[Triple listener]
    HL --> R[路由与 Filter Chain]
    DL --> R
    GL --> R
    TL --> R
    R --> U1[HTTP upstream]
    R --> U2[Dubbo2 upstream]
    R --> U3[gRPC upstream]
    R --> U4[Triple upstream]

2.1 HTTP 入口：先匹配路由，再执行 HTTP filter

HTTP 请求从 pkg/listener/http/http_listener.go 的 DefaultHttpWorker.ServeHTTP 进入网络 filter chain。pkg/common/http/manager.go 的 HttpConnectionManager 创建请求上下文、通过 RouterCoordinator 匹配 method + path，然后依次执行 HTTP filter，最后把上游响应写回客户端。

最常见的反向代理配置是：

1
2
3
4
5
6
7

http_filters:
  - name: dgp.filter.http.httpproxy
    config:
      timeout: 800ms
      maxIdleConns: 400
      maxIdleConnsPerHost: 100
      maxConnsPerHost: 200

pkg/filter/http/httpproxy/routerfilter.go 会根据路由选择 cluster endpoint，复制原始 method、path、query、body 和 header，使用 net/http client 调用上游。

另一条 HTTP API 集成路径在 pkg/filter/http/remote/call.go：integrationRequest.requestType 为 http 时调用 HTTP client；为 dubbo 或 triple 时，映射 URI/query/header/JSON body 为 RPC 参数后，走 pkg/client/dubbo。这就是“HTTP 开放 API，后端仍是 Dubbo/Triple 服务”的典型落点。

2.2 HTTP 到 gRPC：JSON 不是直接原样转发

dgp.filter.http.grpcproxy 的实现位于 pkg/filter/http/grpcproxy/grpc.go。它会：

  1. 从 URL 拆出服务名和方法名；
  2. 根据本地 .proto 或服务端 reflection 获取 descriptor；
  3. 把 HTTP JSON body 解码为动态 Protobuf message；
  4. 把 HTTP headers 变成 gRPC metadata；
  5. 通过 gRPC 调用下游，并把 Protobuf 响应重新编码为 JSON。

例如客户端可发送：

1
2
3
4

POST /example.UserService/GetUser
Content-Type: application/json

{"id":42}

网关实际对下游执行的是 GetUser(GetUserRequest{id: 42})。这也是为什么协议转换不只是“改一层 header”：它需要可靠的接口描述来判断字段类型。

2.3 Dubbo 和 Triple 的出站协议由配置明确指定

在 API 定义中，Triple 后端使用 requestType: triple，Dubbo2 使用 requestType: dubbo。pkg/client/dubbo/dubbo.go 的 protocolReferenceOption 将 tri/triple 映射为 WithProtocolTriple()，将 dubbo 映射为 WithProtocolDubbo()；同一处还把负载均衡、重试次数和请求超时交给 Dubbo-go client。

1
2
3
4
5
6

integrationRequest:
  requestType: triple
  applicationName: UserProvider
  interface: com.example.UserService
  method: GetUser
  clusterName: user-provider

这里有一个重要边界：不要因为 Pixiu 有协议转换能力，就在每个热点接口上随意做 JSON <-> Protobuf 转换。转换会带来解析、分配和 descriptor 查询成本。外部 API 用 HTTP/JSON、内部主链路用 gRPC 或 Triple 是常见折中，但应由实际调用方和性能数据决定。

3. 高并发不是一个开关：一次请求经过哪些保护

下面以“库存接口突然被压到 2 万 QPS，而库存服务只能稳定处理 5 千 QPS”为例。

1
2
3
4
5
6
7

客户端
  -> HTTP listener：读写/空闲超时与请求头大小上限
  -> Sentinel 限流：超额请求直接在网关返回
  -> 路由：从健康 endpoint 中选择实例
  -> HTTP Transport：复用连接，并限制单 host 连接数
  -> Sentinel 熔断：连续 5xx 后快速失败
  -> 库存服务

目标不是让网关“无限接单”，而是让它在超载时有序拒绝、在下游变慢时及时释放资源、在实例故障时避开坏节点。

3.1 入口边界：先阻止慢连接占满资源

HTTP listener 创建 http.Server 时，在 pkg/listener/http/http_listener.go 设置：

  • ReadTimeout：限制读取客户端请求的时间；
  • WriteTimeout：限制向客户端写响应的时间；
  • IdleTimeout：限制 keep-alive 空闲连接；
  • MaxHeaderBytes：限制请求头大小。

默认值分别是 20 秒、20 秒、20 秒和 1 MiB，均可在 listener 的 config 中覆盖。

1
2
3
4
5

config:
  read_timeout: 5s
  write_timeout: 5s
  idle_timeout: 30s
  max_header_bytes: 1048576

这类限制主要防御慢请求和异常大 header。假如攻击者每隔几秒只发送一点请求头，没有 ReadTimeout，连接可能长期占用服务端资源；有了超时，网关会在规定时间内结束该连接。

要注意 WriteTimeout 与 SSE/长流的关系。HttpConnectionManager 的代码本身也留下了 stream 场景需要重新评估 server WriteTimeout 的注释。长连接和普通 API 不该直接照抄同一组超时。

3.2 对象复用：减少 GC，不是限制并发

pkg/common/http/manager.go 中的 HttpConnectionManager 使用 sync.Pool 复用 Pixiu 的 HttpContext：

1
2
3
4
5
6
7

hc := hcm.pool.Get().(*pch.HttpContext)
defer hcm.pool.Put(hc)

hc.Writer = w
hc.Request = r
hc.Reset()
hcm.Handle(hc)

它复用的是请求处理过程中的工作台对象，不是 Go 标准库的 context.Context，也不是连接。

1
2
3

请求 A -> Get(ctx-1) -> 独占 ctx-1 -> 处理完成 -> Put(ctx-1)
请求 B -> Get(ctx-2) -> 独占 ctx-2
请求 C -> pool 暂无空闲对象 -> 创建新的 HttpContext

所以 sync.Pool 不会让请求互相共享上下文，也不会在池空时阻塞请求，更不是一个固定大小的 worker pool。它的价值是减少临时对象分配和 GC 压力。

代码审查时还应特别关注复位逻辑。pkg/context/http/context.go 的 Reset() 会清掉路由、响应和本地回复状态，但当前不会清空 Params map。Params 被熔断 filter 用来暂存 Sentinel entry，因此任何 filter 若把请求数据放进 Params，都应自行覆盖或清理，避免把可变请求状态留给后续复用。

3.3 上游连接池与连接上限：别把下游一口气压垮

pkg/filter/http/httpproxy/routerfilter.go 的 Apply() 只在 filter 初始化时创建一个 http.Client 和 http.Transport，请求处理时复用它：

1

3
4

factory.client = http.Client{
    Timeout: cfg.Timeout,
    Transport: &http.Transport{
        MaxIdleConns:        cfg.MaxIdleConns,
        MaxIdleConnsPerHost: cfg.MaxIdleConnsPerHost,
        MaxConnsPerHost:     cfg.MaxConnsPerHost,
    },
}

这三项配置的含义不同：

配置 解决的问题
MaxIdleConns 限制整个 Transport 可保留的空闲连接数
MaxIdleConnsPerHost 避免空闲连接过度集中在一个上游
MaxConnsPerHost 限制到一个 host 的总连接数，超出时请求在 Transport 内等待可用连接

例如库存服务有 4 个实例，每实例预计可承受 50 条并发 TCP 连接，可先为单个 Pixiu 实例设置合适的 MaxConnsPerHost，再结合 Pixiu 副本数计算总量。这个数字不能照抄示例：网关有 10 个副本时，200 * 10 可能已经超过单个下游实例的承受范围。

同一 HTTP proxy filter 也使用 http.Client.Timeout。上游超时会映射为 504；无可用 endpoint 返回 503。及时结束无望请求，才能防止 goroutine、连接和排队时间不断累积。

3.4 限流：把超过下游能力的流量挡在入口

Sentinel 限流 filter 的 kind 是 dgp.filter.http.ratelimit。pkg/filter/sentinel/ratelimit/rate_limit.go 根据 URL 匹配 resource，然后调用：

1
2
3

entry, blockErr := sentinel.Entry(resourceName,
    sentinel.WithResourceType(base.ResTypeAPIGateway),
    sentinel.WithTrafficType(base.Inbound))

这里的 Entry 不是“登记一条配置”，而是一次请求进入 Sentinel 保护链的动作。Sentinel 会把 resourceName 包装成资源上下文，然后依次执行统计、流控等 slot。调用结果有两种：

1
2
3
4
5
6
7
8

Entry("inventory")
  -> 没有违反规则：返回 (*SentinelEntry, nil)
       -> 继续访问下游
       -> 请求结束时 entry.Exit()

  -> 违反规则：返回 (nil, *BlockError)
       -> 不访问下游
       -> Pixiu 返回 429

resourceName 来自 Pixiu 自己的 matcher：pkg/filter/sentinel/config.go 定义资源和 path pattern，pkg/filter/sentinel/matcher.go 负责把 /inventory/42 匹配成资源名，例如 inventory-api。只有匹配成功的 URL 才会调用 Entry；没有配置资源的 URL 会直接跳过该 filter。

放行时必须调用 entry.Exit()，它告诉 Sentinel “这次进入已经结束”，让并发数、响应时间和结果统计能够闭合。Pixiu 的限流 filter 用 defer entry.Exit()，所以即使后面的 filter 返回或发生错误，也会结束这次 entry。被阻塞时 Entry 已经返回 BlockError，不应该再调用一个不存在的 entry；Pixiu 直接构造 RateLimited 本地响应并停止 filter chain。

其规则在 Apply() 初始化，并通过 OnRulesUpdate() 加载启用的 flow rules。flow rule 至少要说明三件事：管哪一个 Resource、阈值 Threshold 是多少、超过阈值时是直接拒绝还是排队等待（ControlBehavior）。例如统计窗口是 1 秒、阈值是 4000，那么含义是“该 resource 每秒最多按 4000 次的预算放行”，不是“整个 Pixiu 进程只能处理 4000 个请求”。

对 /inventory/*，限流的业务含义可以是：库存服务的预算是 5 千 QPS，网关留出余量后只放行 4 千 QPS；多出来的请求快速失败或由客户端退避重试，而不是排队到库存服务、把所有正常请求一起拖慢。

限流阈值应该来自压测和线上指标。只写一个很高的固定 QPS，不能称为容量治理。

3.5 熔断：下游连续失败时快速失败

dgp.filter.http.circuitbreaker 位于 pkg/filter/sentinel/circuitbreaker/circuit_breaker.go。它同样先为匹配的资源执行 Sentinel entry；熔断器已经打开时，直接返回 503，不再继续调用下游。

在 encode 阶段，它会把 HTTP 5xx 标记为 Sentinel error：

1
2
3

if statusCode >= 500 && statusCode < 600 {
    entry.SetError(err)
}

这里的 entry 生命周期跨越了“请求发出”和“响应回来”两个阶段：熔断 filter 在 Decode 阶段调用 Entry，把返回的 entry 放进 HttpContext.Params；请求经过 HTTP proxy 到达上游后，在 Encode 阶段读取它、根据最终状态码调用 SetError，最后 entry.Exit()。这样 Sentinel 才能把一次完整调用的成功、失败和耗时记到同一个资源上。

熔断规则和限流规则也不是一回事。限流主要问“现在进来的速度是否超过预算”；熔断主要问“最近这个下游是否持续失败或过慢”。Sentinel 的 circuit-breaker rule 可以选择：

  • ErrorCount：错误次数达到阈值；
  • ErrorRatio：错误比例达到阈值；
  • SlowRequestRatio：超过 MaxAllowedRtMs 的慢请求比例达到阈值。

规则达到条件后，熔断器进入 open 状态，新的 Entry 直接得到 BlockError，Pixiu 返回 503，不再制造新的下游请求。经过 RetryTimeoutMs 后进入 half-open，只放少量 probe request 探测；探测成功才恢复 closed，失败则继续 open。也就是说，熔断不是永久关闭接口，而是一个“失败统计 -> 快速失败 -> 试探恢复”的状态机。

这形成闭环：失败响应被 SetError 记录，达到配置规则后熔断器打开；恢复窗口后只允许少量请求试探。当前 filter 把 HTTP 5xx 视为错误，业务级 HTTP 4xx 不会因为这段代码自动计入熔断错误。

它和限流解决的是不同问题：

机制 问题 例子
限流 入口流量超过系统预算 秒杀突然冲到 2 万 QPS
熔断 下游正在失败或不可用 库存数据库故障，接口持续 5xx

两者可以叠加，但都需要按路由配置资源与规则；不能仅因代码里有 filter，就认为所有流量默认已受保护。

3.6 健康检查与负载均衡：只从健康节点里选

pkg/server/cluster_manager.go 的 PickEndpoint() 从 runtime cluster 的不可变 endpoint snapshot 取出健康节点，再调用负载均衡器。没有健康 endpoint 时直接返回 nil，上层代理回 503。

pkg/cluster/cluster.go 在健康检查结果变化时发布新的 snapshot；pkg/cluster/loadbalancer/load_balancer.go 把健康 endpoint 集合作为选址输入。Round-robin 的游标使用原子操作；遗留的可变负载均衡实现会经 mutex 串行化，以避免并发选择污染状态。

因此一次 HTTP、Dubbo、gRPC 或 Triple 的代理调用虽然协议不同，但都会经过类似的 endpoint 选择逻辑。将失效实例从候选集去掉，比请求失败后盲目重试更能保护整体延迟。

3.7 RPC 的 deadline、重试和流式连接

HTTP 到 gRPC 的转换路径在 pkg/filter/http/grpcproxy/grpc.go 使用 context.WithTimeout(c.Ctx, c.Timeout)，这个 deadline 同时约束 dial 和 invoke；超时映射为 504。Dubbo/Triple generic client 则在 pkg/client/dubbo/dubbo.go 将 request_timeout、retries 和负载均衡选项传给 Dubbo-go。

重试必须谨慎。查询这类幂等操作可以设置有限次数和明确超时；扣款、创建订单等非幂等操作，未经幂等键或去重设计，不应仅为了“高可用”而自动重试，否则一次失败可能变成多次业务写入。

网络 gRPC proxy 还有一条更适合原生流的实现：pkg/filter/network/grpcproxy/filter/proxy/grpc_proxy_filter.go 用并发安全的连接缓存按 endpoint 复用出站 ClientConn，并清理不健康连接；reflection 工作则用 singleflight 合并同一地址的并发查询。它避免了高峰期多个请求同时为同一目标重复建连、重复拉取描述符。

3.8 优雅停机：扩缩容时别半路掐断正常请求

HTTP listener 的 ShutDown() 调用 Go http.Server.Shutdown(ctx)；gRPC listener 在 pkg/listener/grpc/grpc_listener.go 中先拒绝新 stream、等待活跃调用，再执行 GracefulStop()，到期限后才强制停止。listener manager 还以全局 deadline 协调多个 listener 关闭。

这让滚动发布或缩容不至于立即断开正在处理的请求。它不是替代 readiness/liveness、负载均衡摘流或 Kubernetes preStop 的完整方案，但提供了网关进程内必须具备的最后一道收尾。

总结

Pixiu 的高并发能力不是靠单一组件实现的。首先它基于 Go net/http 和 goroutine 承载大量并发请求，并通过 ReadTimeout、WriteTimeout、IdleTimeout 等机制防止慢连接长期占用资源。

请求处理过程中，Pixiu 使用 sync.Pool 复用 HttpContext，减少高 QPS 下临时对象分配和 GC 压力。

在调用下游时，HTTP Proxy 会复用 http.Client 和 http.Transport 的连接池，避免每次请求重新建立 TCP 连接，同时通过 MaxConnsPerHost 和 Client Timeout 控制对单个上游的连接和等待成本。

流量治理方面，Pixiu 集成 Sentinel。RateLimit Filter 在入口根据资源规则限制 QPS，超过预算的请求直接在网关快速失败；CircuitBreaker 则统计下游 5xx、错误率或慢请求，在下游持续异常时打开熔断器，避免继续向故障服务发送请求。

最后，ClusterManager 会从健康 endpoint 中结合负载均衡算法选择实例，避免持续把请求发给故障节点。

所以本质上是“提高单请求处理效率 + 限制资源占用 + 入口限流 + 下游熔断 + 健康实例负载均衡”，共同保证高并发下不会因为流量突增或下游异常导致系统雪崩。

这里给一个完整的流程图 客户端 │ │ 入站 HTTP Request ↓ Go http.Server │ ↓ sync.Pool.Get(HttpContext) │ ┌─────────┴─────────┐ │ HttpContext │ │ Request │ │ Params │ │ Route │ └─────────┬─────────┘ │ ↓ Sentinel RateLimit “流量是否太大？” │ 放行 ↓ Sentinel CircuitBreaker Decode阶段 │ 创建 entryA │ 存入 Params ↓ HTTP Proxy │ 选择 endpoint │ http.Client │ http.Transport │ ┌────────┴────────┐ │ TCP连接池 │ │ Conn1 Conn2 … │ └────────┬────────┘ │ keep-alive ↓ 库存服务 │ HTTP Response ↑ │ Sentinel CircuitBreaker Encode阶段 │ 从 Params 取 entryA │ 5xx → entryA.SetError() │ entryA.Exit() │ ↓ 返回客户端 │ HttpContext ↓ sync.Pool.Put()

5. 面试中可以怎样在 60 秒内回答

我不会把高并发归结为一个连接池。Pixiu 的 HTTP 入口先用 ReadTimeout、WriteTimeout、IdleTimeout 和 MaxHeaderBytes 限制慢连接与异常请求；热路径中 HttpConnectionManager 用 sync.Pool 复用请求工作台，降低分配和 GC，但它不限制并发。对上游，HTTP proxy 初始化时复用 http.Client/Transport，并可通过 MaxConnsPerHost 约束对单个实例的连接压力。流量超过预算时，Sentinel 限流在 filter chain 前段直接拒绝；下游持续 5xx 时，熔断器快速返回 503。路由从健康 endpoint snapshot 中做负载均衡，发布时 HTTP 和 gRPC listener 都支持优雅停机。生产上还要把这些阈值和多副本、监控、压测绑定，不能只靠默认值。

这段回答的重点不在于罗列名词，而在于把每个机制对应到它保护的资源：入口连接、内存分配、上游连接、下游容量、故障扩散和发布过程。

6. 读源码时应保留的边界

最后几个边界比“功能清单”更重要：

  • Pixiu 当前没有一个通用的、有界 worker pool；不要把 sync.Pool 描述为 worker pool 或并发闸门。
  • MaxConnsPerHost 只约束配置了 httpproxy filter 的 HTTP 出站连接，不能推导为所有协议共用的全局并发上限。
  • 限流和熔断是可插拔 filter，必须实际配置资源和规则才会生效。
  • 自动重试会放大流量和副作用。只对幂等操作、可恢复错误和明确重试预算使用。
  • 超时的层次要一致：入口读写超时、网关到上游的 client deadline、业务自身超时应共同设计；任意一层过长都可能占住资源，过短又会制造无效失败。

理解这些边界后，HTTP、Dubbo2、gRPC 和 Triple 就不再是四个孤立名词：它们是进入同一套网关治理链路的不同载体，而高并发能力来自沿链路逐层设定预算和隔离。
